# Runbook：runbook 编写与维护

## 适用场景

- 新增、拆分、合并、移动或删除 runbook，或调整 runbook 的结构、命名与索引。
- 本文规定 runbook 的写法与维护方式；具体工程流程见各主题 runbook。

## 前置读取

- [Runbook 全局索引](index.md)
- [文档写作](docs/docs-writing.md)

## 原则

1. **可执行**：每篇能照着做完，给前置条件、判定标准、步骤与通过标准，不写主题框架。
2. **单一出处**：一个主题一个文件，规则只写一次，其他位置用相对链接引用。
3. **入口薄、细则深**：入口只保留流程、选择与验收；细节下沉到主题分册，分册必须有 `README.md` 索引。
4. **结构与索引同步**：新增、拆分、移动、改名时，同一任务内更新全局索引、目录树、触发表与全部入链。
5. **流程与形式分离**：怎么做写在流程 runbook，文档或产物长什么样写在 `docs/` 或对应形式 runbook。
6. **命名准确**：文件名由「对象 + 方面」构成，读者不打开文件即可判断内容；不用工作类型或过程词（`task`、`fix`、`note`、`misc`）。
7. **可发现**：每个会修改仓库的场景都能从触发表找到入口；没有对应 runbook 时先新建或扩展现有文件。
8. **依赖单向**：入口 → 分册单向；入口不把分册内容列为前置，分册不要求先读入口才能使用；同一分组内的分册可互相引用，但不复制规则。
9. **变更传播**：修改规则前检索全部引用者，同一任务同步下游 runbook、`docs/` 与触发表；直接改原文，不保留旧版规则与兼容分支。
10. **真实可核实**：命令、路径、字段使用仓库中的真实值；占位符统一，示例不虚构。
11. **术语一致**：同一概念全文同一名称，跨 runbook 以首次定义处为准；标识符、命令、路径与日志保留原文。
12. **单一约束**：一条规则只围绕一个主题；同一主题的同类约束可合条，不同主题必须拆条。
13. **定期审计**：每个版本收尾检查孤儿、重复、失效引用与过期规则，发现问题直接修文件。

## 章节结构

每篇 runbook 必备：

| 章节 | 内容 |
| --- | --- |
| 适用场景 | 何时使用、何时不用 |
| 前置读取 | 完成本主题必需的单向上游，0–2 篇；没有上游时不设本节 |
| 相关（可选） | 非必读的关联 runbook 链接，不参与前置依赖 |
| 规则 / 设计要点 | 约束、判定标准与取舍依据；可按主题命名，如 `日志`、`指标`、`顶层结构` |
| 步骤 | 编号步骤，命令可复制，产物明确 |
| 验证 | 可检查的通过标准；无法验证时写明原因 |

- 规则用列表，字段与对照用表格，步骤用编号列表，命令与输出用代码块并标注语言。
- 每条规则给出判定标准或反例，避免「应尽量」「视情况」这类无法执行的表述。
- 一条规则只围绕一个主题；同一主题的同类约束可合条，不同主题拆成多条，不用「并且」「同时」把无关约束拼在一起。
- 规则部分可按主题命名，但必须包含约束与判定标准；「规则 / 设计要点」只是默认标题。
- 目录索引 `README.md` 只维护索引与阅读顺序，不受五段结构约束。
- 前置读取只列完成本主题必需的单向上游，通常 0–2 篇；任一篇的递归前置不超过 5 篇、500 行。同级与下游关系写入文末「相关」段。
- 前置读取不得成环：被前置的文档不得直接或间接前置当前文档；入口 runbook 不把分册内容列为前置，分册不反向要求读完入口。
- 同一概念全文使用同一名称，跨 runbook 以首次定义处为准；标识符、命令、路径与日志保留原文，不翻译。
- 一篇能完整读完；出现两个以上可独立成篇的子主题，或篇幅超出单次阅读范围时拆分。
- 不写决策过程、备选方案、历史版本与聊天结论；结论直接写进承载它的规则。
- 不复制其他 runbook 的内容；跨主题用相对链接指向原文件。
- 命令、路径、字段使用仓库中可核实的值；占位符统一为 `<...>`（按项目填写）与 `{{...}}`（项目接入时替换），示例不虚构项目名或不存在的命令。

## 归属与拆分

- 先判断内容类型：流程进阶段分组；工程规则进 `engineering/`；文档与产物的形式进 `docs/`；runbook 自身的维护规则写在根目录 `runbook.md`。
- 端差异（服务端/客户端）写在同一主题文档内并按端分节；同一端形成两个以上独立主题时，按端建立分册目录。
- 场景已有 runbook 覆盖时更新原文件，不新建近似文档。
- 拆分条件：出现两个以上可独立成篇的子主题，或单篇超出一次完整阅读范围。拆分后入口保留流程、选择与验收，细则移入分册。
- 分册之间不重复规则；同一规则只写一处，其余链接过去。
- 合并或删除前先检索全库引用与章节锚点，确认无入链后再删除文件。

## 目录规划

- 一级目录按职责与阶段划分：`docs/`（文档形式）、`version/`（版本流程）、`product/`（产品与 UI）、`engineering/`（工程规则）、`implementation/`（实施）、`delivery/`（交付）、`problems/`（排障）。
- 一级目录不按技术栈、端（服务端/客户端）或文件类型划分；端差异写在所属主题文档内，或按端建立分组下的分册目录。
- 分组内单主题文件平铺；同一子领域出现两个以上文件、或单篇需要拆分时，才建子目录并增加 `README.md` 作为分册索引（如 `docs/structure/`、`engineering/server/`、`product/ui/`）。
- 只有一个文件的子领域不建子目录，直接平铺在分组内，避免为单个文件增加层级。
- 目录层级最多两级（分组 → 分册），不再向下嵌套；更深的内容用一篇文档内的章节承载。
- 分册目录（一级分组下的子目录）必须有 `README.md`，列出本分册文件与一句话说明；一级分组不设 `README.md`，由根目录树与[全局索引](index.md)承载。
- `runbooks/` 根目录另有[全局索引](index.md)，登记全部 runbook，与目录树、触发表保持一致。
- 新增一级目录前先确认现有分组无法承载，并在[全局索引](index.md)、[目录树](README.md)与根 `AGENTS.md` 触发表登记。
- 删除或移动目录时同步索引与入链，不留空目录与孤儿文件。

## 命名规范

- 文件与目录统一小写 kebab-case、`.md` 扩展名；使用英文，专有名词与技术词（`ui`、`api`、`schema`、`worktree`）直接使用。
- 名称用名词短语表达主题（`schema-change`、`ui-design`），不用工作类型或过程词（`task`、`fix`、`update`、`note`、`misc`）。
- 一个文件只表达一个主题；文件名不与所在目录同名，入口文件统一用 `README.md`。
- 分组目录用职责名词（`docs`、`version`、`engineering`）；分册目录用子领域名词（`ui`、`structure`、`server`、`client`）。
- 不使用版本号、日期、人名与含义不明的缩写；名称控制在两到三个词。
- 标题 `#` 与文件名一致并使用名词短语；改名时同步更新全部入链与锚点引用。

### 同目录一致性

- 同一目录内的文件名保持同一词序：修饰语在前、主题在后（如 `directory-structure`、`schema-change`），不混用前后缀表达同一含义（`x-docs` 与 `docs-x` 不同时出现）。
- 同类文件使用同一后缀：同一目录内表达同类含义的文件统一后缀，如 `-change`、`-design`、`-runtime`、`-docs`；新增同类文件沿用已有后缀。
- 单复数按语义统一：集合、清单用复数（`pages`、`components`、`tokens`），单一概念或流程用单数（`theme`、`interaction`、`bugfix`）。
- 新增文件前先对照同目录现有命名，沿用其词序、后缀与单复数；无法沿用时不长期并存两种模式，先统一已有文件或在索引中说明例外。
- 目录内文件超过两个时，命名应能归纳为一到两条模式；归纳不出时先整理命名，再新增文件。

### 名称准确性

- 文件名由「对象 + 方面」组成，读者不打开文件即可判断内容：用 `ui-docs-structure`（UI 文档的结构），而不是 `ui-docs`（只有对象）。
- 对象本身已是完整主题时可用对象名（`pages`、`icons`、`theme`）；对象是泛集合或文档类、单靠对象无法判断内容时，必须补充方面词。
- 方面词按实际内容选择，并与正文范围一致：`structure`（结构）、`writing`（写作）、`sync`（回写）、`change`（变更）、`design`（设计）、`runtime`（运行）。
- 名称不宽于内容：只定义结构就不用 `-design`；不窄于内容：正文包含落点、职责与生命周期时，要么选能覆盖全文的方面词，要么拆分文档。范围变化时同步改名或收窄内容。
- 不只用对象命名（`docs`、`ui`、`server`），也不用不承载信息的方面词（`info`、`misc`、`materials`）。
- 同目录的同类文件使用同一方面词；同类文件改名时一并评估，避免 `x-docs` 与 `x-docs-structure` 并存。
- 改名判据：读者需要打开文件才知道它写什么，或两个文件名无法区分职责时，必须改名。
- 改名在同一任务内完成：`#` 标题、正文中的称谓、全部入链与链接文字、索引、触发表与章节锚点引用一并更新，不留旧名引用。

## 索引与同步

- [全局索引](index.md)是 runbook 的唯一登记处：每个 runbook 一行，含分组、文件与一句话适用场景；新增、改名、移动或删除时，同一任务内同步本表，不留「已废弃」条目。
- `README.md` 只维护目录树与项目基线，不重复登记单个 runbook。
- 根 `AGENTS.md` 触发表只登记「场景 → 文件」的映射，是唯一路由入口；新增场景先补 runbook 与触发行，不留无入口的流程。
- 修改规则前全库检索引用者（runbook、`docs/`、代码与 `AGENTS.md`），同一任务同步更新；直接改原文，不保留旧版规则、兼容分支或旧做法说明。
- `docs/`、其他 runbook 与代码中的引用一并更新；改标题锚点时全库检索。
- 每次调整后校验相对链接与锚点，清理被替代的旧文件。

## 审计

- 每个版本收尾检查：孤儿文件、重复主题、失效引用、过期规则与触发表缺口。
- 发现问题直接修改文件；不新建审计记录、问题清单或历史变更日志。
- 无法立即调整的跨版本事项写入对应版本的 `open-questions.md`，结论确定后回到文件修改。
- 审计完成后校验相对链接与锚点，确认触发表覆盖所有会修改仓库的场景。

## 步骤

1. 判断场景是否已有 runbook 覆盖；有则更新原文件。
2. 确定分组、文件名与层级（入口或分册），文件名按「对象 + 方面」核对是否准确。
3. 按章节结构写内容，规则可判定、步骤可执行、验证可检查。
4. 更新全局索引、目录树、触发表与全部入链，并同步引用被改规则的 runbook、`docs/` 与代码。
5. 校验链接与锚点，删除被替代的文件或空目录。

## 验证

- 每篇具备适用场景、规则部分、步骤与验证；前置读取与相关按需设置；目录索引 `README.md` 除外。
- 规则有判定标准，无复制内容、无决策过程与备选方案。
- 拆分后入口与分册职责清晰，分册有 `README.md` 索引。
- 命名符合 kebab-case 与主题命名，无过程词、同义重复与不明缩写。
- 文件名由对象与方面组成，或对象本身即完整主题；读者无需打开即可判断内容。
- 同类文件方面词一致。
- 标题、链接文字与文件名一致，改名后无旧名残留。
- 同一目录内词序、后缀与单复数一致，或例外已在索引中说明。
- 目录层级不超过两级，单篇子领域未建子目录，分册目录有 `README.md`。
- 入口与分册依赖单向，无「入口 ↔ 分册」循环；同级分册引用不复制规则。
- 前置读取无环，任一 runbook 的递归前置不超过 5 篇、500 行；非必读关联已放入「相关」段。
- 术语全文一致，标识符、命令与路径保留原文；占位符统一，示例可在仓库核实。
- 每条规则只围绕一个主题；不同主题的约束已拆条。
- 触发表覆盖所有会修改仓库的场景；无孤儿文件、重复主题、失效引用与过期规则。
- 全局索引覆盖 `runbooks/` 下全部 runbook，无遗漏、无死链。
- 索引、目录树、触发表与入链一致，无死链、坏锚点与孤儿文件。
