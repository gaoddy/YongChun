# Runbook：任务计划

## 适用场景

- 进入实施阶段后跟踪任务进度，或在合并前清理计划。
- 计划文件的结构与命名见[文档结构](../docs/structure/docs-structure.md#实施计划-plan)。

## 前置读取

- [文档结构](../docs/structure/docs-structure.md)

## 规则

- 计划目录只在实施计划时创建和使用；只读任务、小改动以及尚未进入实施的任务不建计划目录。
- 计划写在 `docs/plan/<分支名>/`，一个计划一个目录；`docs/plan/` 已加入 `.gitignore`，不提交。
- 阶段顺序固定：产品确认 → 技术确认 → 任务拆分；前一阶段未确认时不进入下一阶段，也不产出后续文件。
- 计划只管理任务执行；产品与技术结论放在 `update/`，计划中链接引用，不复制。
- 任务按可独立验证的粒度拆分；每个任务明确文件边界，多个任务不并发写同一文件。
- 实施阶段按任务派发子 agent 执行；子 agent 统一使用主 agent 的 worktree，派发与隔离规则见[Worktree 与分支](../implementation/worktree.md)。
- 并行任务之间没有依赖才可同时进行；有依赖的按顺序排列并在计划中写明。
- 范围变化时先改计划再改代码；实施中的偏离记录在计划里。
- 纯文档或规则任务在计划中注明无产品改动与技术实现。
- 任务完成后、合并前删除当前计划目录；目录不进入提交，不处理历史计划。

## 步骤

1. 确认任务所属版本、关联的需求目录与分支名。
2. 产品与技术确认完成后进入实施阶段，按[文档结构](../docs/structure/docs-structure.md#实施计划-plan)在 `docs/plan/<分支名>/` 建立计划目录与文件。
3. 拆分任务，写清每个任务的输入、产出、文件边界与验证方式。
4. 实施中更新任务状态与偏离说明；范围变化时先更新计划。
5. 任务完成后、合并前删除当前计划目录，确认未进入提交。

## 验证

- 计划在产品与技术确认完成后创建，未确认阶段不产出任务规划。
- 计划目录只在实施计划时存在，只读任务与小改动没有计划目录。
- 每个任务可独立验证，文件边界清晰，并行任务无文件重叠。
- 计划未复制 `product.md`、`technical.md` 的内容，只保留链接。
- `docs/plan/` 不参与提交，任务完成后计划目录已删除，worktree 已清理。
