# Runbook：周期复盘

## 适用场景

- 版本收尾或固定周期，需要分析交付效率与质量数据并沉淀改进。
- 分析最近一段时间的 PR 时长、卡点、Bug、返工、回滚与重复修改，找出共同根因。
- 不用于单次故障定位与修复；单次问题按[问题排查](../problems/troubleshooting.md)与[缺陷修复](bugfix.md)处理。

## 规则

### 数据窗口

- 明确起止日期、统计口径与数据来源：已合并 PR、未合并 PR、缺陷记录、回滚记录与重复修改的文件；结论必须能用同一口径复核。
- 数据从仓库与平台直接获取（`git log`、PR 列表、缺陷目录、发布记录），不依赖记忆或口头描述。
- 样本不足或数据缺失时写明缺口与影响，不把缺失数据按 0 处理。

### 交付卡点

- PR 按阶段拆分耗时：首次提交 → PR 创建 → 首次评审 → 评审通过 → CI 通过 → 合并；分别统计等待评审、等待 CI、返工与排队时间。
- 找出耗时最长的若干个 PR，逐个写明卡在哪个阶段、直接原因与可消除的流程因素；不只统计平均值。
- 区分个人因素与流程因素；只把流程因素沉淀为规则、自动化或工具，个人因素不写入 runbook。

### 质量与返工

- 统计窗口内的缺陷、返工、回滚与重复修改，逐个记录发现阶段（开发、测试、发布、线上）与触发原因。
- 对每个事件追问到共同根因：需求不清、验证缺口、契约或生成物不同步、流程缺失、依赖变化、环境差异等；同一根因合并计数。
- 同类问题再次发生时，先检查已有规则为何未生效；修补原规则，不新增重复条目。

### 改进沉淀

- 每个共性根因对应至少一项可执行改进，按成本从低到高选择：补 runbook 规则、补测试或检查项、加 CI 或 hook 自动化、新增或调整 Skill 与 agent。
- 每项改进写明落点文件、触发方式与验证方式；「加强评审」「提高意识」这类无法验证的表述不作为改进项。
- 改进在下一个窗口复盘时验证是否生效：同类问题数量下降或拦截阶段前移；未生效时修改方案，不重复登记。

### 结论落点

- 规则改进直接写入对应 runbook，自动化写入 `scripts/` 或 CI 配置，Skill 与 agent 按[Runbook 与 Agent 映射](../runbook-agent-mapping.md)更新。
- 不新建复盘报告、问题清单或历史变更日志；结论直接进入承载它的规则、测试或自动化。

## 步骤

1. 确定窗口、统计口径与数据来源，拉取 PR、缺陷、返工、回滚与重复修改数据。
2. 按阶段拆分 PR 耗时，找出最慢的 PR 与共同卡点。
3. 逐个复盘质量事件，记录发现阶段与原因，聚合成共同根因并计数。
4. 为每个共性根因选择成本最低的有效改进，写明落点、触发方式与验证方式。
5. 与用户确认改进项后实施：改 runbook、补测试、加自动化或调整 Skill。
6. 在下一窗口核对改进是否生效；未生效时修改方案。

## 验证

- 窗口、口径与数据来源明确，结论可用同一口径复核。
- PR 耗时按阶段拆分，最慢项有卡点与流程因素说明。
- 质量事件逐个记录发现阶段与原因，共同根因已合并计数。
- 每个共性根因都有可执行的改进项，写明落点与验证方式，无「加强评审」类表述。
- 改进已落地到 runbook、测试或自动化，未新建复盘报告。
- 下一窗口已核对改进效果，未生效项已修改方案。
