# Runbook：决策记录

## 适用场景

- 需要记录一项今后不应被重新推翻的决策：架构形态、技术选型、边界划分、有意的偏离常规做法，或已否决的需求与方案。
- 新需求或新方案与既有结论相似，需要先判断是否已否决过。
- 本文只规定记录什么、怎么写；记录落在 `docs/` 的哪个目录由[文档结构](../docs/structure/docs-structure.md)决定。

## 规则

### 何时记录

- 记录门槛：同时满足三类条件才写入：
  1. 逆转成本高：改变结论需要返工架构、数据、契约或已发布版本。
  2. 脱离上下文会费解：后来者看现状会问「为什么不是另一种做法」。
  3. 存在真实权衡：有可选的替代方案，选择基于具体原因。
- 任一条件不满足时不记录：容易逆转的结论直接改；不令人费解的结论无需解释；没有替代方案的结论只写实现，不写「决策」。

### 两类记录

- 已采用的决策：记录结论、原因、排除的替代方案与影响面；替代方案的否决理由只在非显而易见时写入。
- 已否决的请求：一个概念一个文件，记录否决结论、实质理由与全部历史请求；理由写项目范围、技术约束或战略取舍，不写「暂时没空」这类延期理由。

### 写法

- 一条记录只写一个决策或一个被否决的概念，标题是结论或概念名，不用「关于 X 的说明」。
- 记录结论与原因即可；原因必须能解释「后来者为什么不能照直觉改」，不重复需求、技术方案或版本基线的内容。
- 写明排除的替代方案与排除理由，防止后继评审再次提出同一方案。
- 已否决记录的「历史请求」逐条列出请求来源与日期；同一概念的新请求追加到同一文件，不新建副本。
- 决策被推翻时直接改写原记录并注明当前结论，不保留旧结论作为备选。

### 何时不记录

- 可逆的选择、只影响当前实现的细节、已有 runbook 规则覆盖的内容，均不记录。
- 不新建决策日志、评审记录或历史变更列表；结论只进入承载它的记录。

## 步骤

1. 判断候选是否同时满足三条记录门槛；不满足时直接写明为何不记录。
2. 判断类型：已采用的决策或已否决的请求。
3. 检索既有记录，存在同一概念时追加或改写，不新建副本。
4. 按写法写结论、原因与排除的替代方案，并在所属索引登记。
5. 需要引用该决策的 runbook 或文档用相对链接指向记录，不复述内容。

## 验证

- 每条记录都能说明一条以上否决理由，且理由指向项目范围、技术约束或战略取舍。
- 检索全部记录，不存在同一决策或同一否决概念的多份文件。
- 记录未复制 `product.md`、`technical.md` 或 runbook 规则的内容。
- 决策被推翻时原记录已改写，不残留旧结论。
- 索引与入链完整，无死链。
