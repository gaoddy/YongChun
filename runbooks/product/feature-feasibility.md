# Runbook：产品功能可行性调研

## 适用场景

- 产品需求已经澄清并确认，需要确认当前技术能否实现、受哪些约束、与现有功能是否冲突。
- 产品需求仍有待确认项时，先按[产品功能需求澄清](feature-requirements.md)完成澄清，不进入本调研。

## 前置读取

- [产品功能需求澄清](feature-requirements.md)

## 输入

- 已确认的产品需求：`update/<需求>/product.md` 或版本 `product/` 基线。
- 现有实现：相关页面、接口、数据结构、依赖与共享层。

## 调研维度

| 维度 | 必须查明 |
| --- | --- |
| 现有能力 | 相关页面、接口、数据结构、依赖与共享层；哪些可直接复用，哪些需要新增或改动 |
| 技术实现 | 平台与框架是否支持；需要引入的第三方服务或依赖；关键链路能否在目标端实现 |
| 数据与权限 | 新增或变更的字段、数据量、迁移方式；角色与越权处理是否可实现 |
| 性能与容量 | 峰值请求、存储增长、渲染与响应延迟；是否触及现有容量上限 |
| 冲突 | 与既有功能规则、数据模型、交互与导航、权限、资源占用、发布策略的冲突点 |
| 成本与风险 | 开发与维护成本、依赖稳定性、灰度与回滚方式、不可逆点 |

- 依据必须可核实（仓库代码、官方文档或实测结果），不写「应该可以」「大概支持」。
- 每个冲突点写明受影响的功能或数据、冲突表现与处理方式（调整产品需求、修改既有功能或分阶段上线）。
- 不因工程难度、改造成本或历史包袱把可行结论改成不可行；成本与风险照实列出，由用户决定是否接受。

## 结论

| 结论 | 含义 | 后续 |
| --- | --- | --- |
| 可行 | 全部维度无阻塞，可按产品需求实现 | 进入需求变动 |
| 有条件可行 | 存在前置条件或需要调整范围 | 条件写入产品需求，用户确认后进入需求变动 |
| 不可行 | 当前技术或现有约束下无法实现 | 给出替代方案或排除理由，回到产品需求澄清 |

- 结论为「有条件可行」或「不可行」时，先回到[产品功能需求澄清](feature-requirements.md)调整并重新确认产品需求，不在调研阶段直接改产品规则。

## 结论落点

| 结论 | 落点 |
| --- | --- |
| 产品需求的条件或调整 | `docs/versions/<版本>/update/<需求>/product.md`，按[需求变动](../version/requirement-change.md) |
| 可行性约束与冲突处理 | 产品确认后写入 `technical.md`，不提前写技术方案 |
| 无法确认的事项 | 版本 `open-questions.md`，写明问题、影响范围与待确认方 |
| 调研过程 | `docs/drafts/<主题>.md`，结论回写后删除 |

## 步骤

1. 读取已确认的 `product.md` 或版本产品基线，确认没有待确认项；存在时停止并回到需求澄清。
2. 盘点相关页面、接口、数据结构、依赖与共享层，列出可复用与需改动项。
3. 按调研维度逐项给出结论与可核实依据。
4. 列出全部冲突点、成本与风险，给出可行、有条件可行或不可行的结论。
5. 与用户确认结论；有条件可行与不可行时先调整并重新确认产品需求。
6. 按[需求变动](../version/requirement-change.md)进入技术确认；有条件可行时先把条件写回 `product.md`，未决项写入版本 `open-questions.md`，删除讨论记录。

## 验证

- 输入只有已确认的产品需求，没有待确认项。
- 调研覆盖现有能力、技术实现、数据与权限、性能与容量、冲突、成本与风险六个维度。
- 每条依据可在仓库、官方文档或实测结果中核实，无「应该可以」「大概支持」这类表述。
- 每个冲突点写明受影响对象与处理方式。
- 结论为三种之一；有条件可行写明前置条件，不可行给出替代方案或排除理由。
- 未提前写 `technical.md` 或拆分任务。
- 未决事项只在版本 `open-questions.md`，讨论记录已删除。
