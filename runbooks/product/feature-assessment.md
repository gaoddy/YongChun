# Runbook：产品功能评估

## 适用场景

- 计划新增产品功能、扩大既有功能范围或引入新能力，实施前需要完成产品需求澄清与技术可行性确认。
- 纯缺陷修复、纯技术改动与文案排版调整不适用，分别按[缺陷修复](../version/bugfix.md)、[技术选型变更](../engineering/tech-change.md)与普通任务处理。
- 产品规则落地为文档见[产品定义文档](product-definition.md)，结论进入版本见[需求变动](../version/requirement-change.md)。

## 前置读取

- [产品定义文档](product-definition.md)
- [讨论记录](../implementation/discussion-record.md)

## 阶段与顺序

| 阶段 | 只讨论 | 完成条件 | 未完成时 |
| --- | --- | --- | --- |
| 一、产品需求澄清 | 产品规则、页面、状态、权限、字段与验收 | 无待确认项、每条规则可验收、用户确认 | 不进入阶段二 |
| 二、可行性调研 | 技术实现、约束、冲突、成本与风险 | 给出可行、有条件可行或不可行结论 | 缺条件时回到阶段一调整范围 |

- 阶段顺序不可跳过：产品需求未澄清前不讨论技术实现；可行性调研未完成前不写 `technical.md`、不拆分任务。
- 阶段二发现问题会改变产品规则时，回到阶段一确认；不在调研结论中直接改产品规则。

## 阶段一：产品需求澄清

- 按[产品定义文档](product-definition.md)的要素逐项写清：定位与用户、范围、功能规则、页面与交互、状态与边界、角色与权限、数据与字段、验收标准。
- 只写产品层面；技术实现、接口、表结构、依赖与成本一律记录为待评估项，留到阶段二。
- 每条规则写成可观察、可验收的行为；无法判定的表述（如「体验更好」）改为具体结果。
- 明确本次不做的内容与原因，避免范围在阶段二被技术可行性反向扩大。
- 过程结论按[讨论记录](../implementation/discussion-record.md)记录：尚未建立需求目录时写 `docs/drafts/<主题>.md`，已建立 `update/<需求>/` 时直接更新 `product.md`；每条标注「已确认」「待确认」或「已否决」。

## 阶段二：可行性调研

- 输入只有阶段一已确认的产品需求；产品需求存在未确认项时停止，不凭推测评估。
- 按以下维度逐项给出结论与依据；依据必须可核实（仓库代码、官方文档或实测结果），不写「应该可以」「大概支持」。

| 维度 | 必须查明 |
| --- | --- |
| 现有能力 | 相关页面、接口、数据结构、依赖与共享层；哪些可直接复用，哪些需要新增或改动 |
| 技术实现 | 平台与框架是否支持；需要引入的第三方服务或依赖；关键链路能否在目标端实现 |
| 数据与权限 | 新增或变更的字段、数据量、迁移方式；角色与越权处理是否可实现 |
| 性能与容量 | 峰值请求、存储增长、渲染与响应延迟；是否触及现有容量上限 |
| 冲突 | 与既有功能规则、数据模型、交互与导航、权限、资源占用、发布策略的冲突点 |
| 成本与风险 | 开发与维护成本、依赖稳定性、灰度与回滚方式、不可逆点 |

- 每个冲突点写明受影响的功能或数据、冲突表现与处理方式（调整产品需求、修改既有功能或分阶段上线）。
- 结论只能取以下三种，并写明判断依据：

| 结论 | 含义 | 后续 |
| --- | --- | --- |
| 可行 | 全部维度无阻塞，可按产品需求实现 | 进入需求变动 |
| 有条件可行 | 存在前置条件或需要调整范围 | 条件写入产品需求，用户确认后进入需求变动 |
| 不可行 | 当前技术或现有约束下无法实现 | 给出替代方案或排除理由，回到阶段一 |

- 不因工程难度、改造成本或历史包袱把可行结论改成不可行；成本与风险照实列出，由用户决定是否接受。

## 结论落点

| 结论 | 落点 |
| --- | --- |
| 已确认的产品需求 | `docs/versions/<版本>/update/<需求>/product.md`，按[需求变动](../version/requirement-change.md) |
| 可行性约束与冲突处理 | 产品确认后写入 `technical.md`，不提前写技术方案 |
| 无法确认的事项 | 版本 `open-questions.md`，写明问题、影响范围与待确认方 |
| 调研过程 | `docs/drafts/<主题>.md`，结论回写后删除 |

## 步骤

1. 写清功能设想：目标用户、使用场景、期望结果与明确不做；尚无需求目录时建立 `docs/drafts/<主题>.md`。
2. 按阶段一逐项澄清产品需求，只讨论产品层面，结论逐条落盘。
3. 核对完成条件：无待确认项、每条规则可验收、用户确认；未满足时继续澄清，不进入阶段二。
4. 按阶段二的维度盘点现有实现，逐项给出结论与可核实依据。
5. 列出全部冲突点、成本与风险，给出可行、有条件可行或不可行的结论。
6. 与用户确认结论；有条件可行与不可行时先调整并重新确认产品需求。
7. 按[需求变动](../version/requirement-change.md)写 `update/<需求>/product.md`，未决项写入版本 `open-questions.md`，删除讨论记录。

## 验证

- 阶段一完成前没有进行技术可行性讨论，也没有写 `technical.md` 或拆分任务。
- 每条产品规则可验收，无待确认项，用户已确认。
- 可行性结论覆盖现有能力、技术实现、数据与权限、性能与容量、冲突、成本与风险六个维度。
- 每条依据可在仓库、官方文档或实测结果中核实，无「应该可以」「大概支持」这类表述。
- 每个冲突点写明受影响对象与处理方式。
- 结论为三种之一；有条件可行写明前置条件，不可行给出替代方案或排除理由。
- 未决事项只在版本 `open-questions.md`，讨论记录已删除，结论可在 `product.md` 中找到。
