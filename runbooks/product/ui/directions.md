# Runbook：方向方案

## 适用场景

- UI 设计与改版开始前，向用户呈现可比较的方向并取得选择。
- 设计与实现流程见[UI 设计](ui-design.md)；本文只规定方向方案的内容与约束。

## 前置读取

- [UI 设计](ui-design.md)

## 规则

### 方案数量与范围

- 所有 UI 相关任务（包括设计与改版）都先给出三种完整且彼此可区分的方向，供用户比较；用户已明确指定方向时不重复要求选择。
- 每种方向覆盖所有受影响页面或组件，不只覆盖局部。
- 每个方向说明：
  - 页面结构与布局层级；
  - 视觉语言，包括色彩、字体、图形、间距和组件表现；
  - 关键操作与交互反馈；
  - 适用状态：加载、空态、错误、禁用、选中及不同业务阶段（只列适用状态）；
  - 与方向对应的可视化方案，例如页面草图、流程图、关键状态图或可运行原型。

- 可视化应足以比较完整体验，不能只给换色示意。

### 现状基线

- 先了解当前代码、页面和已有交互，区分已实现功能、设计建议与尚未实现能力；不得把推测描述成现有功能。
- 改版方向必须以当前代码中确认存在的功能和流程为基础，说明如何呈现和改善这些功能，不得自行增加业务功能。
- 可以调整信息架构、布局、UI 交互方式与交互流程，但不得自行新增业务能力或修改业务规则。
- 用户已明确指定方向时，直接采用该方向，不再生成备选。

### 新增功能

- UI 设计或概念探索允许提出新功能；每项新功能须标明「新增功能（设计提议，尚未实现）」，并说明它解决的用户问题及关键交互、状态。
- 交互调整须说明目的及关键交互状态，不得将提议混写为现有能力。

## 步骤

1. 确认现有实现与受影响页面、组件，列出需要覆盖的业务状态。
2. 按方案范围写出三种可区分方向，每个方向补齐布局、视觉、交互、状态与可视化。
3. 对照现状基线，标注每项功能的来源：现有实现、交互调整或新增功能。
4. 呈现比较并取得用户选择；用户已指定时直接采用。
5. 选定方向交给[UI 设计](ui-design.md)的分册继续细化。

## 验证

- 三种方向在结构、视觉或交互上确有差异，均覆盖全部受影响页面/组件。
- 每种方向写明布局、视觉语言、关键操作与反馈、适用状态及可视化。
- 每项功能可追溯到现有实现，或被标为交互调整、新增功能（设计提议，尚未实现）。
- 用户已确认方向，或已有明确的指定方向。
