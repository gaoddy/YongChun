# Runbook：前端方案设计

## 适用场景

- 产品改动已确认，编写 `update/<需求>/technical.md` 的客户端部分。
- 不影响产品的纯技术改动，直接编写 `technical.md` 的客户端方案。

## 前置读取

- [客户端分层](layering.md)
- [UI 设计](../../product/ui/ui-design.md)

## 设计要点

| 维度 | 方案中必须写明 |
| --- | --- |
| 改动边界 | 受影响的页面、组件、状态与接口调用，逐项对应 `product.md` 的页面与交互规则 |
| 分层落点 | 页面、状态、数据源分别落在哪一层；通用部分是否进入共享设计层 |
| 页面与交互 | 页面清单、入口与返回路径、加载中 / 空态 / 错误 / 无权限 / 离线的表现，以及交互与反馈时机 |
| 状态管理 | 状态作用域、provider 分层、刷新与失效规则、跨页面共享的数据与生命周期 |
| 数据层 | 调用的接口、参数与分页、超时与重试、错误映射与提示、本地缓存与失效 |
| 导航与深链 | 路由组织、参数传递、返回栈、深链与外部唤起 |
| 性能 | 首屏与列表渲染、分页与预取、图片与资源、重建范围与动画开销 |
| 适配与可用性 | 不同屏幕尺寸与真机、无障碍标签、弱网与空数据处理 |
| 测试设计 | 需要验证的页面与链路、数据来源（真实接口或固定快照），验证后测试文件的清理 |

## 数据驱动界面

- 每个页面明确数据源：接口、参数、分页方式、超时与重试、缓存与失效。
- 状态作用域按页面或功能划分，不建全局万能状态；跨页面共享的数据单独定义生命周期与刷新规则。
- 页面不直接发请求，通过数据层获取；接口字段与错误码以服务端方案为准。
- 每个数据状态映射到唯一界面状态：加载中、空、错误、无权限、离线、达到限额；不允许同时出现互相矛盾的状态（如加载中同时展示空态）。
- 错误区分可重试与不可重试：可重试给重试入口，不可重试给返回或升级出口；用户文案不暴露技术细节。
- 刷新明确触发条件（进入页面、下拉、轮询、事件）与停止条件；轮询在页面不可见或数据稳定时停止。
- 写操作提交中禁用并防重复提交；成功后局部更新或重新拉取；失败保留用户输入。
- 乐观更新只在可回滚时使用，并定义失败回滚与提示。
- 离线时明确可读缓存范围与写操作处理策略。

## 方案取舍

- 比较维度只考虑：架构的合理性、可维护性、可扩展性与长期演进能力，以及性能、资源占用、响应延迟和吞吐；部署维度按客户端发布形态评估升级与灰度影响。
- 可说明实施成本与风险，但不因工程难度、改造成本、历史包袱或兼容负担降低推荐标准。

## 步骤

1. 读取已确认的 `product.md` 与版本 `technical/` 基线，确认产品规则不再变动。
2. 按设计要点逐项写出方案，标注涉及的页面、组件、状态与接口。
3. 通用视觉与交互优先复用共享设计层；需要新增通用组件时在设计要点中说明扩展方式。
4. 接口字段与错误码以服务端方案为准，发现缺失或冲突时写入版本 `open-questions.md`。
5. 与用户确认方案后，把 `technical.md` 状态改为「方案未实施」，并把确认结论同步到版本 `technical/` 基线。
6. 方案变更时更新原文件，不新建目录或副本。

## 验证

- `product.md` 中每条页面与交互规则都能在方案中找到落点。
- 页面、状态与数据层的依赖方向符合客户端分层约束，通用能力进入共享设计层。
- 每个页面状态（加载、空、错误、无权限、离线）均有明确表现，数据状态与界面状态一一对应且无矛盾。
- 刷新有明确触发与停止条件；写操作防重复、失败保留输入，乐观更新有回滚。
- 接口调用与错误处理覆盖服务端方案中的全部错误码。
- 未确认事项已进入 `open-questions.md`，方案中无未决分支。
