# Runbook：代码库审计

## 适用场景

- 评估现有设计是刻意为之还是历史遗留，判断哪些代码可以安全移除。
- 评估新工程师接手项目所需的认知成本，寻找命名、抽象与职责问题并提出简化方案。
- 需要结合 Git 历史、关键 PR 与架构演变说明现状来历时使用。

## 规则

### 历史取证

- 每条结论给出证据：`git log` 或 `git blame` 的提交、关键 PR、变更前后的文件路径；只凭当前代码猜测来历的结论不成立。
- 区分三类设计：有意为之（有明确目标与约束）、历史遗留（当时的约束已消失）、为已不存在的问题引入（问题已由其他机制解决）；三类分别记录保留或移除理由。
- 对疑似历史包袱，先确认是否仍有调用方、外部契约、数据迁移或运行时依赖在使用；无法确认时标为「待确认」，不进入移除清单。
- 移除判定必须可执行：同时给出引用检索、测试覆盖与运行时信号三类证据；任一缺失时只提出收敛方案，不直接删除。

### 认知成本

- 以「明天接手、不了解项目」的工程师视角走查：从入口到完成一个典型任务，记录需要打开的文档、理解的抽象与跨越的目录。
- 逐项列出高成本点：命名与实际职责不符、抽象层数超过需要、同一职责分散在多处、必须了解历史才能读懂的隐式约定、无边界名称（`util`、`common`、`manager`、`helper`）。
- 每个高成本点写清理解它需要的前置知识、影响的文件范围与简化后的预期收益（减少的文件、层数或概念数）。

### 简化方案

- 每次只提出一个可独立验证的简化：改动范围、预期减少的代码或概念、风险与回退方式；不把简化与功能改动打包在同一任务。
- 简化优先顺序：删除无调用方的代码 → 合并重复职责 → 收敛抽象层 → 修正命名；不先做大规模目录迁移。
- 简化后必须通过现有测试与静态检查；缺少测试覆盖时先补特征测试，再改结构。

### 结论落点

- 审计结论写入版本 `technical/` 或 `docs/current/technical/` 的对应模块文档，按[文档写作](../docs/docs-writing.md)与[文档回写](../docs/docs-sync.md)回写；不新建审计报告、问题清单或历史变更日志。
- 可立即执行的简化按[任务执行与交付](../implementation/change-delivery.md)进入任务；无法立即执行的写入版本 `open-questions.md`。

## 步骤

1. 明确审计目标与范围：历史包袱、认知成本或两者；列出目标目录、模块与时间窗口。
2. 收集 Git 历史、关键 PR、架构文档与当前实现，按「有意设计 / 历史遗留 / 已不存在问题」分类并附证据。
3. 对疑似可移除项核对调用方、外部契约、数据迁移与运行时依赖，形成可移除、需收敛、保留三张清单。
4. 以新工程师视角走查典型任务，列出认知成本点及所需前置知识。
5. 按优先级提出单一、可独立验证的简化方案，写明收益、风险与回退方式。
6. 与用户确认后按[任务执行与交付](../implementation/change-delivery.md)实施；结论回写承载文档，未决项写入版本 `open-questions.md`。

## 验证

- 每条历史结论都有提交、PR 或文件路径证据，且区分三类设计。
- 可移除清单中的每项都有引用检索、测试覆盖与运行时信号证据；缺证据的项只列为需收敛。
- 认知成本清单写清前置知识、影响范围与简化收益。
- 简化方案单一可验证，未与功能改动打包，风险与回退方式明确。
- 结论已回写承载文档，未新建审计报告；未决项只在版本 `open-questions.md`。
