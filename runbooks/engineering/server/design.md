# Runbook：后端方案设计

## 适用场景

- 产品改动已确认，编写 `update/<需求>/technical.md` 的服务端部分。
- 不影响产品的纯技术改动，直接编写 `technical.md` 的服务端方案。

## 设计要点

| 维度 | 方案中必须写明 |
| --- | --- |
| 改动边界 | 受影响的服务端模块、接口、表与生成物，逐项对应 `product.md` 的规则 |
| 分层落点 | 逻辑放入 handler / domain / application / infrastructure 的哪一层；新增端口由谁定义、由谁实现、在何处装配 |
| 接口契约 | 路径、方法、请求与响应字段、错误码、分页与过滤；复用或新增 `/api/v1/...` 接口 |
| 数据 | schema 变更、约束与不变量、事务边界、幂等键；迁移形式按[项目阶段](../../../AGENTS.md#项目阶段) |
| 并发与一致性 | 锁、隔离级别、重试与去重、缓存一致性、跨服务写入顺序 |
| 部署与扩展 | 无状态化、多实例并行、滚动更新期间的兼容、后台任务与定时任务的分片与幂等、健康检查影响 |
| 可观测性 | 关键日志字段、指标、错误码与告警触发点 |
| 性能与容量 | 查询与索引、分页、批量、缓存、限流，以及预期的数据量与延迟 |
| 失败与降级 | 外部依赖的超时、重试、熔断、降级与补偿 |
| 测试设计 | 端到端测试覆盖的链路与真实依赖，`<e2e 入口>` 执行范围 |

## 方案取舍

- 比较维度只考虑：架构的合理性、可维护性、可扩展性与长期演进能力、部署上的平滑扩展能力，以及性能、资源占用、响应延迟和吞吐。
- 可说明实施成本与风险，但不因工程难度、改造成本、历史包袱或兼容负担降低推荐标准。

## 步骤

1. 读取已确认的 `product.md` 与版本 `technical/` 基线，确认本次改动不属于产品规则讨论。
2. 按设计要点逐项写出方案，标注涉及的模块、接口、表与文件位置。
3. 对存在多种可行方案的点写出取舍与理由，按上面的方案取舍标准比较，不以实施成本降低标准。
4. 未确认的事项写入版本 `open-questions.md`，不在方案中留待定分支。
5. 与用户确认方案后，把 `technical.md` 状态改为「方案未实施」，并把确认结论同步到版本 `technical/` 基线。
6. 方案变更时更新原文件，不新建目录或副本。

## 验证

- `product.md` 中每条产品规则都能在方案中找到对应实现位置。
- 接口、schema 与生成物的变更点均可定位到具体文件与命令。
- 依赖方向符合分层约束：跨层依赖面向抽象接口，实现只在入口装配。
- 部署形态满足无状态与多实例并行，无单实例假设。
- 未确认事项已进入 `open-questions.md`，方案中无未决分支。
