# Runbook：服务架构方案生成

## 适用场景

- 项目初始化、新版本或重大需求需要确定服务端架构，架构方向尚未确定时。
- 架构方向已确定、只需细化实现方案时，直接按[服务端方案实现](implementation.md)执行。

## 输入

- 产品需求：版本 `product/` 基线或 `update/<需求>/product.md`，逐条列出功能、角色、数据与访问要求。
- 产品描述：项目事实中的产品名、产品描述与产品形态，见[项目接入](../../implementation/project-init.md)。
- 用户规模：项目事实中的最终总用户数与日活；缺失时先确认，不自行假设。
- 现有实现：已有项目列出当前架构、数据量、性能瓶颈与已知问题；新项目写明无。

## 方案要求

- 默认给出三种完整、彼此可区分的方案供用户选择；用户已指定架构方向时直接采用，不再生成备选。
- 三种方案都必须满足产品需求与最终用户规模，差异体现在技术形态、复杂度与演进路径，不得以「先低配、以后再扩容」的方式降低容量标准。
- 每个方案必须写明：

| 部分 | 必须写明 |
| --- | --- |
| 技术选型 | 语言、框架、数据库、缓存、消息队列、任务调度与部署形态；每项注明理由与被排除的替代项，选型原则按[技术选型变更](../tech-change.md) |
| 软件架构 | 服务边界（单体、模块化单体、微服务）、模块划分（依赖方向按[服务端分层](layering.md)）、同步与异步边界、数据归属与一致性策略、外部依赖 |
| 平滑扩容 | 按最终用户规模推算的容量基线（峰值 QPS、存储增长、连接数，写明假设与公式）；扩容单元与顺序（纵向、横向、读写分离、分片、缓存分层）；触发指标与阈值；扩容期间的不停机要求与兼容处理 |
| 成本与风险 | 部署与运维复杂度、人力与云资源量级、主要风险与规避方式 |
| 适用前提 | 方案成立的前提（团队规模、预算、上线节奏、合规要求）与不适用场景 |

- 容量推算写明假设、公式与峰值集中系数；日活不能直接当作 QPS，峰值按业务场景估算并标注依据。
- 平滑扩容给出从当前容量到最终用户规模的分步路径与每一步的触发条件，不写「支持横向扩展」这类无法执行的结论。
- 三种方案在关键取舍上不同：例如托管服务与自建、单体与拆分、强一致与最终一致；不能只更换技术名称。

## 输出与选择

- 方案写入 `docs/versions/<版本>/technical/architecture-options.md`，首行标注「待选择」，按[版本文档结构](../../docs/structure/version-docs-structure.md)放置；新项目写入首个版本目录。
- 先给对比表列出关键差异（技术形态、容量上限、扩展方式、复杂度、成本、适用前提），再逐个方案展开；只写给选择必需的信息，不写完整实施方案。
- 标明推荐方案与理由；用户选定后按[服务端方案实现](implementation.md)把选定方案细化为技术方案，其余方案删除，选定结论并入版本技术基线。
- 用户提出修改或新方向时，按新输入重新生成三种方案，不把旧方案作为备选保留。

## 步骤

1. 读取产品需求、产品描述、用户规模与现有实现，确认输入齐全；缺失项写入版本 `open-questions.md` 并向用户确认。
2. 按最终用户规模推算容量基线，记录假设、公式与峰值集中系数。
3. 写出三种可区分方案，每个方案补齐技术选型、软件架构、平滑扩容、成本与风险、适用前提。
4. 用对比表呈现差异并标明推荐方案，向用户呈现并取得选择。
5. 用户选定后按[服务端方案实现](implementation.md)细化方案，写入版本技术基线，删除候选文件中的其余方案。

## 验证

- 三种方案均覆盖全部产品需求与最终用户规模，没有降低标准的降级方案。
- 每个方案都包含技术选型、软件架构、平滑扩容、成本与风险、适用前提。
- 容量推算有假设与公式，平滑扩容有触发条件与分步路径。
- 方案之间存在实质差异，不是同一架构更换技术名称。
- 用户已完成选择，选定方案进入版本技术基线，候选文件无残留备选方案。
