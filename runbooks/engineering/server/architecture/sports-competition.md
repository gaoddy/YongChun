# Runbook：体育竞技架构

## 适用场景

- 设计高帧率体育竞技（足球、篮球、赛车等）的服务端架构。
- 与实时对战分册的区别是强制确定性物理、裁判判定与赛后回放：比赛结果必须能由锁定的物理参数与输入完整复现，进球、犯规、越位、计时等判定由服务端裁决并写入回放。
- 不适用于不要求物理复现或赛后回放的实时对战，也不适用于回合制与弱在线玩法；这些场景回到[服务架构方案生成](index.md)的场景路由选择分册。

## 规则

### 同步模型

- 比赛服按固定 tick 推进，每个 tick 执行固定步长的物理模拟；tick 频率与物理步长在同一场比赛内不变，物理步长取值为 `<每物理步毫秒数>`，且物理步与 tick 的比值固定，不在运行中动态调整。
- 客户端输入带时间戳上报，比赛服按输入延迟补偿处理：补偿窗口取 `<补偿窗口毫秒数>`，窗口内的输入并入对应 tick 的物理步，超出窗口的输入丢弃并记录，不做无上限追帧。
- 比赛服在收到迟到输入时回滚到该输入目标 tick 的状态并重演，重演只使用该时刻已确定的输入集合，重演完成后再追赶当前 tick。
- 进球、犯规、越位、出界、计时与胜负等裁判逻辑全部在比赛服按规则代码判定，客户端只上报输入与本地表现，不上报判定结果。
- 判定：若物理模拟只存在于客户端、服务端仅转发输入，或裁判判定由客户端上报并被采信，说明方案不满足本场景，必须把物理与裁判逻辑移回比赛服。

### 确定性

- 物理引擎版本、碰撞与摩擦等参数、随机种子与比赛规则版本，随每场回放一起锁定并写入回放头；回放读取时按锁定版本复原，不使用当前线上默认参数。
- 同一场次中，服务端实时模拟、赛后回放与断线重演必须使用同一份锁定配置与同一版本二进制，三者产生的结果一致。
- 物理模拟使用定点数或整数，不使用跨硬件不可复现的浮点路径；回放一致性以逐 tick 状态哈希比对，不以容差范围内的近似结果替代。
- 判定：同一回放在相同锁定版本下重跑，逐 tick 状态哈希与实时记录完全一致；出现差异时定位到版本、参数、随机源或浮点，不通过放宽容差掩盖。

### 候选架构差异

- 单场一实例的比赛服：一场比赛绑定一个比赛服实例，实例持有该场的 tick 循环、物理状态、输入流水与裁判状态；比赛结束后实例释放，不跨场复用内存状态。
- 匹配与赛季服分离：匹配服只负责组队、场地分配与实例调度，赛季服负责赛季规则、积分与排行；两者都不参与单场 tick。
- 回放存储与比赛服分离：回放按场次写入对象存储或独立库，比赛服只负责生成与上传，回放读取、观看与导出不占用比赛服的 tick 与写路径。
- 观战走独立广播通道：比赛服把观战所需状态发布到观战广播服务，由观战服务按频率裁剪并分发；观战连接不直接挂在比赛服的比赛写路径上。
- 三种方案必须写明比赛服、匹配与赛季服、观战服务、回放存储的边界与部署形态，并在实例打包方式、观战通道与回放存储形态上存在实质差异；不能只更换技术名称。
- 判定：若方案让观战连接直接订阅比赛服的比赛写路径，或把赛季结算放进单场比赛服进程同步执行，即不符合本分册的边界要求。

### 容量指标

- 比赛模拟 CPU 峰值按 `并发场次 × 每秒 tick 数 × 每 tick 物理步数 × 单物理步开销` 估算；单物理步开销按受控实体数与碰撞对数实测取值，不按玩家数估算。
- 回滚重演 CPU 追加开销按 `并发场次 × 每秒回滚次数 × 每次回滚重演帧数 × 单物理步开销` 估算，并与实时模拟开销相加得到比赛服 CPU 峰值；重演帧数取补偿窗口覆盖的物理步数上限。
- 并发场次按最终用户规模与同时开赛比例推算，写明假设、公式与峰值集中系数；日活不能直接当作并发场次。
- 观战连接数按 `并发场次 × 每场观战人数` 推算，与比赛连接分开统计；观战下行带宽按 `观战广播频率 × 观战包大小 × 观战连接数` 估算，观战连接数不得并入比赛服的 tick 容量计算。
- 回放存储增长按 `每日场次 × 每场回放时长秒数 × 每回放秒数据量` 估算，每回放秒数据量包含输入流水与锁定物理参数，并分别写出月度与年度增长及保留周期对应的总量。
- 判定：每个方案都能复算出比赛模拟 CPU 峰值、回滚重演追加开销、并发场次、观战连接数与回放存储增长五个量，并标注假设与峰值集中系数。

### 平滑扩容

- 以场次为单位扩展：新增比赛服实例即增加可承载的并发场次；比赛进行中不跨实例迁移，实例故障时该场按已记录输入与最近状态快照重演或判负结束，实例之间不共享物理状态。
- 观战与比赛分离扩容：观战广播服务按观战连接数与出网带宽独立扩容，比赛服按 tick 与物理负载扩容，两者使用不同触发指标，不共用一台实例的容量预算。
- 赛季结算与排行异步：赛季积分结算、排行刷新与奖励发放走异步任务或独立批处理，不阻塞比赛服 tick；结算失败可重试，不因结算回滚比赛结果。
- 匹配与调度分离：调度器按比赛服的实际 tick 耗时与 CPU 选择承载实例，不按连接数分配。
- 判定：扩容期间进行中的比赛不中断，新比赛落到新实例；扩容触发指标与阈值写入方案，并能对应到具体监控量。

### 常见陷阱

- 物理版本漂移：比赛进行中升级物理引擎或修改参数，实时结果与赛后回放不一致；回放必须锁定版本与参数，未锁定版本的回放标记为不可复现。
- 延迟补偿过度：补偿窗口过大或允许无上限追帧，迟到输入反复触发大规模重演，比赛服 CPU 尖峰并拖慢其他场次；补偿窗口设上限，超窗输入丢弃并记录。
- 观战拖慢比赛 tick：观战连接直接挂在比赛服写路径，观战人数增长挤占比赛 tick 时间预算；观战走独立广播服务并按频率裁剪。
- 赛后结算重复：比赛结束信号重复投递或多处触发结算，积分与奖励被多次发放；结算以场次与结算类型为幂等键，重复请求返回首次结果。
- 裁判逻辑双写：客户端本地判定与服务端裁判规则不一致，出现画面进球但判定无效的分歧；判定只认服务端规则代码，客户端表现以服务端结果回正。
- 回放存储无序增长：全量保存每场回放且无保留策略，存储成本随场次线性膨胀；按场次与时长核算增长并写明保留周期与冷热分层。

## 步骤

1. 按[服务架构方案通用要求](requirements.md)读取产品需求、产品描述、用户规模与现有实现，确认属于高帧率、强制确定性物理、需要裁判判定与赛后回放的体育竞技场景；不属于时按[服务架构方案生成](index.md)的场景路由改选分册。
2. 按通用要求的三种方案要求与输出位置生成方案，只展开体育竞技差异部分：固定 tick 与物理步长、输入延迟补偿与回滚重演、裁判逻辑在服务端、物理版本与回放锁定、比赛服/匹配与赛季服/观战服务/回放存储的边界。
3. 按「容量指标」公式为每个方案计算比赛模拟 CPU 峰值、回滚重演追加开销、并发场次、观战连接数与回放存储增长，记录假设与峰值集中系数，写入该方案的平滑扩容部分。
4. 为每个方案写明确定性保障手段、补偿窗口取值、观战广播方式、回放保留策略，以及「常见陷阱」的规避方式；给出以场次为单位的扩容触发指标与阈值。
5. 按通用要求给出对比表与推荐方案，取得用户选择后按[服务端方案实现](../implementation.md)细化选定方案。

## 验证

- 回放与实时结果一致：同一场次的赛后回放在锁定物理版本与参数下重跑，逐 tick 状态哈希与实时记录一致。
- 观战连接不影响比赛 tick：观战人数从零增加到方案中的峰值假设时，比赛服 tick 耗时与物理步耗时在预算内且无额外卡帧。
- 结算幂等：同一场次的结算请求重复投递，积分、排行与奖励只生效一次，重复请求返回首次结果。
- 跨版本回放可标记不兼容：物理版本或参数与回放锁定值不一致时，回放被标记为不可复现或拒绝播放，不静默按当前版本重跑。
- 输入延迟补偿在窗口内生效：窗口内迟到输入被并入对应 tick 并触发有界重演，超窗输入被丢弃且不引起 CPU 尖峰。
- 每个方案写明比赛模拟 CPU 峰值、回滚重演追加开销、并发场次、观战连接数与回放存储增长的假设与公式，平滑扩容以场次为单位并给出触发阈值。
