# Runbook：实时对战帧同步架构

## 适用场景

- 设计固定 tick、确定性输入广播、需要回放复现的实时对战服务端架构。
- 不适用于服务端权威状态同步与回合制；前者由服务端逐帧模拟并下发状态，后者按回合请求-响应，均不要求客户端确定性重放。

## 规则

### 同步模型

- 服务端按固定 tick 收集每位玩家的输入，按 tick 广播完整输入集合；客户端在相同 tick 用相同输入推进模拟，得到一致状态。
- 采用锁定步：第 n 个 tick 的输入收齐或到达截止时间后才推进，未到达的输入按确定规则（保持上一输入或空输入）补齐，补齐规则对全部玩家与重连一致。
- 服务端只收集、排序、转发并校验输入合法性，不做世界模拟；反作弊靠服务端复算关键帧，客户端结果与复算不一致时以复算结果判定或回滚。
- 判定：服务端存在逐帧世界模拟或逐帧下发状态快照，说明方案已偏离帧同步，应改用状态同步方案。

### 确定性前提

- 逻辑运算使用定点数或整数，不使用浮点；浮点在不同硬件、编译器与优化级别下舍入不一致，长时间对局必然分叉。
- 随机数由房间同步种子与 tick 驱动，抽取顺序固定；任一分支使用未同步的随机源即破坏复现。
- 逻辑与渲染分离，模拟步长固定为 `<每 tick 毫秒数>`；渲染插值只影响表现，不回写逻辑状态。
- 同房间客户端与服务端使用同一版本逻辑；版本不一致时拒绝进入或按版本分池，不复用不同版本的回放与快照。
- 判定：同一输入序列重复回放，每一步状态哈希一致；出现不一致时定位到浮点、随机数或版本差异，不通过容差掩盖。

### 断线重连

- 优先按输入重放：房间服保留本房间自开局以来的输入流水，重连客户端从起点或最近关键帧重放。
- 输入流水超出保留窗口或重放开销过大时，改用最近状态快照加后续输入恢复；快照与输入由同一确定性代码生成。
- 重放期间不阻塞其他玩家：房间继续按 tick 推进，重连玩家以追赶模式接收后续输入，追平后进入正常同步；禁止因等待重连玩家暂停房间。
- 判定：重连玩家恢复后的状态哈希与房间权威哈希一致，且其他玩家在重连期间没有额外的 tick 延迟或卡帧。

### 候选架构差异

- 房间是最小单元：匹配服只负责组队与分配，房间服持有单房间的 tick 调度、输入流水与关键帧复算，网关只做连接、鉴权与转发。
- 三种方案都必须写明匹配服、房间服、网关的边界与部署形态；单进程方案也要说明房间隔离方式与后续拆分点。
- 同步通道按场景选择并写明理由：低延迟、可容忍丢包时选 UDP，在应用层实现序号、确认与重传；需要统一长连接或浏览器端接入时选 WebSocket，并写明队头阻塞与重连成本的应对。
- 回放与快照存储独立于房间服：输入流水与关键帧写入对象存储或独立库，房间服重启不依赖内存历史；存储按房间与 tick 分片，回放读取不占用对战链路。
- 判定：三种方案在房间边界、同步通道与回放存储形态上存在实质差异，不能只更换技术名称。

### 容量指标

- 输入带宽按 `tick 频率 × 每房间玩家数 × 输入消息大小 × 房间并发数` 计算，上下行分别统计并按峰值集中系数放大；广播下行随玩家数成倍增长。
- 房间并发数按最终用户规模与同时对局比例推算，推算假设与公式写入方案，日活不能直接当作房间并发数。
- 服务端复算 CPU 峰值按 `房间并发数 × 每 tick 复算开销 × tick 频率` 估算，并计入关键帧复算与并发重放；复算属 CPU 密集项，不能按连接数估算。
- 判定：每个方案都能复算出输入带宽、房间并发数与复算 CPU 峰值三个量，并标注假设与峰值集中系数。

### 平滑扩容

- 以房间为单位水平扩展：新增房间服实例即增加可容纳房间数；同一房间的 tick 与输入处理只在单个实例上，不做跨实例房间迁移，实例故障时房间结束或按快照重建。
- 匹配与房间调度分离：调度器按 tick 延迟与 CPU 负载分配新房间，不按连接数分配。
- 网关无状态，连接可水平扩展；网关与房间服之间按房间标识路由，网关重启不影响房间状态。
- 判定：扩容期间已有房间不迁移、不中断，新房间落到新实例；触发指标与阈值写入方案。

### 常见陷阱

- 浮点漂移：任一逻辑路径使用浮点，长对局后状态分叉；用定点数与每 tick 状态哈希校验。
- 掉线等待造成卡帧：锁定步等待全部输入，房间被慢玩家拖住；用输入截止与确定补齐规则，不对重连玩家暂停 tick。
- 随机数不同步：客户端本地取随机或种子下发时机不一致；随机源统一由房间种子与 tick 决定。
- 输入洪泛：单玩家高频、超长或重复输入挤占带宽与校验资源；按玩家与房间限流，超限丢弃并记录。
- 重连重放开销：长对局全量重放导致重连超时与 CPU 尖峰；用关键帧快照缩短重放区间，并限制并发重放数。
- 单房间 CPU 尖峰：异常输入或复算集中使单房间 tick 超时；为房间设置每 tick 时间预算与过载处理，过载时记录并结束异常房间，不放宽确定性与合法性校验。

## 步骤

1. 按[服务架构方案生成](index.md)读取产品需求、产品描述、用户规模与现有实现，确认属于固定 tick 的帧同步场景；不属于时回到入口按场景路由选择分册。
2. 按入口的三种方案要求与输出位置生成方案，只展开帧同步差异部分：同步模型、确定性前提、断线重连、匹配服/房间服/网关边界、同步通道、回放与快照存储。
3. 按「容量指标」公式为每个方案计算输入带宽、房间并发数与复算 CPU 峰值，记录假设与峰值集中系数，写入该方案的平滑扩容部分。
4. 为每个方案写明确定性保障手段、重连策略与「常见陷阱」的规避方式，并说明以房间为单位的扩容触发指标与阈值。
5. 按入口要求给出对比表与推荐方案，取得用户选择后按[服务端方案实现](../implementation.md)细化选定方案。

## 验证

- 确定性回放结果一致：同一输入序列重放每一步状态哈希相同，服务端关键帧复算与客户端结果一致。
- 掉线重连后状态一致：重连玩家恢复后的状态哈希与房间权威状态一致，重连期间其他玩家 tick 未被暂停。
- 输入校验拦截非法输入：越权、超频、超长与数值越界的输入被拒绝并记录，不进入广播。
- 房间之间互不影响：单房间过载、异常输入或实例故障不改变其他房间的 tick 与状态。
- 每个方案写明输入带宽、房间并发数与复算 CPU 峰值的假设与公式，平滑扩容以房间为单位并给出触发阈值。
- 三种方案在房间边界、同步通道与回放存储形态上有实质差异，且均覆盖全部产品需求与最终用户规模。
