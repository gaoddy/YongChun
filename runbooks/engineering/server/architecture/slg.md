# Runbook：SLG 大战略架构

## 适用场景

- 设计大地图、行军建造、资源产出、联盟与分区开服的大战略 SLG 服务端架构。
- 适用于以分区（服）为部署单元、结算由定时事件驱动、资源与领土要求强一致的产品；不适用于固定 tick 的实时对局与角色持续在场的开放世界，这两类回到[服务架构方案生成](index.md)按场景路由选择分册。

## 规则

### 同步模型

- 弱实时请求-响应：客户端提交指令，服务端在受理时完成校验与资源预占并立即返回受理结果与预计完成时间；实际效果由到期事件结算。判定：接口等到行军到达或建造完成才返回，或以客户端本地计时作为结算依据，均不属于本模型。
- 定时事件驱动结算：行军到达、建造完成、资源产出、伤兵恢复等状态变更以到期事件触发，事件在受理时写入持久化存储并携带唯一事件 ID 与到期时间。判定：靠周期性全表扫描到期行且无到期时间索引、无分片，或依赖客户端上报到期，均为反例。
- 资源与领土强一致：资源扣减、领土归属变更在单玩家或单分区块的串行边界内原子完成，任何并发请求不得读到中间态。判定：先扣资源再异步补写领土、或依赖事后对账修正，为反例。

### 权威边界

- 资源扣减、行军结果、战斗结算、产出结算全部由服务端计算；客户端只提交意图（目标、数量、编队、路径），不提交结果。判定：客户端上报的战斗胜负、资源余量、部队位置或行军速度被直接写入状态，为反例。
- 每条指令在服务端做前置校验：资源是否足够、建造与行军队列是否有空位、冷却是否结束、目标领土归属与视野是否满足；校验与扣减在同一原子操作内完成。判定：校验与扣减分属两个请求或两个事务且中间允许并发插入，为反例。
- 服务端返回的受理结果与结算结果分开：受理只表示指令进入队列，结算结果在事件到期后由服务端推送或客户端查询获得。判定：受理响应中写入最终资源与领土状态，为反例。

### 地图结构

- 地图按固定网格切块，块是行军占用、视野与写入锁的最小单元；块尺寸与块 ID 规则必须在方案中写明。判定：以单个坐标格为锁单元导致锁竞争过高，或以整张地图为锁单元导致全图串行，均为分块错误。
- 跨块行军的归属是行军 ID 而非块：行军路径上的块只校验占用与通行，部队状态在行军归属方（发起分区）的单一权威处更新，到达结算时原子提交目标块的领土与战斗结果。判定：每跨一块就把部队状态迁到该块的存储中分别维护，为反例。

### 候选架构差异

- 分区（服）是部署单元与一致性边界：每个分区独立承载一组玩家、一张地图实例、自己的调度器与业务库；玩家绑定分区，跨分区交互只经跨服服务。判定：全局单库承载所有分区状态，或允许单玩家跨分区直接写分区内资源，为反例。
- 三方案必须在以下五个维度中至少三项取不同形态，并写明各自适用前提；只在语言、框架或云厂商上不同，视为只换技术名称：

| 维度 | 可选形态 |
| --- | --- |
| 地图分块 | 固定九宫格式大块、按活动热点动态细分的小块 |
| 定时调度器 | 内存时间轮加到期落库、延迟队列投递（如 ZSET 延迟集合、队列定时消息） |
| 状态持久化 | 事件溯源加定期快照、状态表直接写当前行加版本号或行锁 |
| 业务库与缓存 | 单库分表、按分区独立库 |
| 跨服战部署 | 独立跨服集群、分区集群内的独立命名空间 |

- 定时调度器形态必须写明事件持久化时机与宕机恢复来源：时间轮方案要写明到期前的持久化队列与重启重载；延迟队列方案要写明投递失败重试与死信处理。判定：只写「定时任务」而不写调度形态与恢复来源，为反例。
- 状态持久化必须选定一套权威机制：事件溯源以事件为权威、快照只用于加速恢复；状态表以当前行为权威、事件只用于结算。判定：两套机制混用且未定义哪一套为权威，为反例。
- 跨服战（王国战、跨服争霸）使用独立集群与独立业务库，不与分区共用写库与调度器；开战期间按场次独立扩缩。判定：跨服战直接读写分区业务库，或与分区争用同一调度器，为反例。

### 容量指标

- 峰值在线人数：`N_peak = N_dau × c_peak`，单位「人」；`N_dau` 为日活（人），`c_peak` 为峰值集中系数（无量纲），按开服日、赛季开启与活动时段的实测峰值在线与日活之比取值，方案必须标注取值依据。判定：直接把日活当作峰值在线人数，为口径错误。
- 定时事件 QPS：`Q_evt = N_peak × r_evt × k_burst`，单位 次/s；`r_evt` 为每活跃玩家每秒到期事件数（次/(人·s)，含行军、建造、产出与治疗；玩家离线后其未结事件仍按到期时间结算，离线玩家的到期事件一并计入，按同时期峰值在线人数归一），`k_burst` 为事件集中系数（无量纲），用于开服排队、赛季结算与整点刷新等同时到期场景。判定：只按平均事件间隔估算而忽略同时到期聚集，或只统计在线玩家的事件而遗漏离线玩家的未结事件，均为反例。
- 地图块写操作 QPS：`Q_blk = N_peak × w_blk`，单位 次/s；`w_blk` 为每在线玩家每秒产生的块写操作数（次/(人·s)，含行军跨块占用、建造落地、采集与领土变更）。判定：把读操作计入该指标或按整张地图一次写入计为一次，均为口径错误。
- 跨服战并发：`C_x = N_peak × p_x`，单位「人」；`p_x` 为同时参与跨服战的在线玩家占比（无量纲）。`跨服战场次 = ceil(C_x / 单场人数)`，单位「场」，`单场人数` 单位为 人/场。判定：用跨服战报名人数代替并发人数，为口径错误。
- 数据库写入 QPS：`W_db = (Q_evt × b_evt + Q_blk × b_blk) × a_w`，单位 行/s；`b_evt` 为单事件结算写入行数（行/次），`b_blk` 为单次块写操作写入行数（行/次），`a_w` 为写放大系数（无量纲，含索引与快照开销）。各因子量纲相乘后为 行/s，不得再把写放大与「每事件行数」重复计入。
- 分区数：`分区数 = ceil(N_peak / 单分区在线上限)`，单位「个」；`单分区在线上限`（人/个）由单分区定时事件 QPS、块写 QPS 与数据库写入 QPS 三项中最早触顶的一项反推，方案必须写明由哪一项约束。判定：只用在线人数决定分区数而不校验其余三项，为反例。
- 判定：每个方案能复算峰值在线人数、定时事件 QPS、地图块写操作 QPS、跨服战并发与数据库写入 QPS 五个量，并给出单分区在线上限的来源；缺少任一项视为容量推算不完整。

### 平滑扩容

- 以分区为单位扩容：一次新增一个或多个分区，新玩家进入新分区，已有分区不迁移玩家；分区数扩容与分区内扩容的触发指标分开定义。分区数扩容的触发指标是单分区在线人数与单分区数据库写入 QPS。
- 地图分块扩容：把块按负载重新分配到地图块工作线程或进程，迁移以块 ID 为单元且先完成落盘再切换归属；触发指标是单块写操作 QPS 与块锁等待时间。
- 调度器分片：按事件键（玩家 ID 或块 ID）把到期事件分配到多个调度分片，每分片独立扫描或消费；触发指标是单分片到期事件 QPS 与结算延迟 P99。扩容时新增分片并重划分键范围，切换期间事件不重不漏。
- 跨服独立部署：跨服战集群与分区集群分开扩缩，按开战场次独立扩容；触发指标是跨服战并发与跨服战场次。
- 开服节奏：分区按预创建计划开服，开服与赛季开启前按 `c_peak` 与 `k_burst` 预留容量并预热缓存；判定：开服首日与赛季开启按平峰容量部署，为反例。
- 判定：扩容期间玩家不掉线、已持久化的定时事件不丢、单分区资源不超发；每项扩容写明触发指标与阈值，并能对应到具体监控量。

### 常见陷阱

- 定时事件丢失或重复：进程重启、重试或多分片重复消费导致事件未触发或触发两次。要求事件持久化、以唯一事件 ID 加玩家 ID 作为幂等键、结算逻辑可重入；反例是到期时间只保存在内存，重启后事件丢失。
- 资源并发扣减超发：两个请求读到同一余额后各自扣减。要求按玩家串行化（单分区单线程队列、行锁或乐观版本），或以 `WHERE amount >= ?` 的条件更新原子扣减；反例是先 `SELECT` 余额再 `UPDATE`。
- 跨区块行军：行军路径跨多个块时各块独立加锁与写入，导致部队重复或中途状态不一致。要求行军以行军 ID 为单一权威、块只做占用校验、到达时原子提交目标块结果；反例是逐块迁移部队所有者。
- 合服数据迁移：合服后玩家 ID、联盟 ID、排行榜与地图坐标冲突。要求先定义 ID 重映射与坐标冲突消解规则，在停服或双写窗口内迁移，并以迁移前后的行数与校验和对账；反例是直接合并同名表而不处理主键与唯一索引冲突。
- 排行榜一致性：排行榜由缓存累加维护，与业务状态不一致且无法重建。要求排行榜由业务事件异步重建、带结算周期与版本号，同一周期内可复现；反例是排行榜作为唯一数据源反向覆盖业务状态。

## 步骤

1. 按[服务架构方案生成](index.md)读取产品需求、产品描述、用户规模与现有实现，确认属于大地图、定时事件驱动、资源与领土强一致的分区式 SLG；不属于时回到入口按场景路由选择分册。
2. 按入口的三种方案要求与输出位置生成方案，只展开 SLG 差异部分：同步模型、权威边界、地图分块与跨块行军归属、五个候选架构差异维度、分区与开服的峰值分布。
3. 按「容量指标」公式为每个方案计算峰值在线人数、定时事件 QPS、地图块写操作 QPS、跨服战并发与数据库写入 QPS，反推单分区在线上限，记录假设、`c_peak` 与 `k_burst`，写入该方案的平滑扩容部分。
4. 为每个方案写明分区扩容、地图分块扩容、调度器分片、跨服独立部署与开服节奏的路径与触发指标，以及「常见陷阱」的规避方式。
5. 按入口要求给出对比表与推荐方案，取得用户选择后按[服务端方案实现](../implementation.md)细化选定方案。

## 验证

- 定时事件幂等：同一事件重放不产生重复扣减或重复奖励；进程重启后未到期与已到期事件都按持久化来源恢复，无丢失。
- 资源扣减不超发：并发指令压测下余额不为负，资源总消耗不超过产出与初始量之和。
- 合服前后数据一致：玩家、联盟、领土、排行榜的数量与校验和在合服前后对齐，ID 与坐标冲突按规则消解。
- 跨服与分区隔离：跨服战读写不落到分区业务库，跨服故障不影响分区内定时事件结算，分区故障不影响已开战场次结算。
- 跨区块行军一致：跨多块行军在到达前部队只出现在权威归属处，到达结算后目标块领土与战果原子可见，无重复部队与中途状态残留。
- 容量可复算：五个容量量均能按公式与假设复算，`c_peak`、`k_burst` 与单分区在线上限有取值依据。
- 三种方案在候选差异维度上至少三项不同，且均覆盖全部产品需求与最终用户规模。
