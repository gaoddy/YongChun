# Runbook：回合制架构

## 适用场景

- 设计回合请求-响应、服务端校验结算、支持异步对战的回合制服务端架构。
- 适用于卡牌、战棋、回合 RPG；不适用于依赖固定 tick 推进的实时 tick 对局。

## 前置读取

- [服务架构方案通用要求](requirements.md)

## 规则

### 同步模型

- 客户端提交动作，服务端校验并结算，再把结果推送给对局参与者；对局状态持久化，支持玩家跨天、离线后继续的异步对战。
- 一次动作的完整链路是「提交 → 校验 → 结算 → 持久化 → 推送」，结算以服务端为准；客户端本地只做表现层的动作预演，不落定状态。
- 判定：若对局状态只在客户端推进、服务端仅记录结果，或服务端返回结算前的推测状态并允许后续被客户端改回，均不符合本模型，必须改为服务端结算后再下发。

### 权威边界

- 随机数、伤害与胜负判定全部在服务端完成；客户端只提交动作意图，例如使用哪张牌、移动到哪个格子、选择哪个目标。
- 随机数由服务端生成并记录到对局日志，重放同一对局时复用记录的随机结果；客户端提交的 seed、随机数或伤害值只能用于反作弊比对，不参与结算。
- 判定：协议中任何字段允许客户端上传伤害值、随机结果或胜负结论并被服务端直接采信，即为越界；随机数若由客户端提供 seed 或取自可预测的时间戳，同样越界。

### 候选架构差异

- 三段拆分：无状态 API 负责动作提交与查询，对局状态存储负责权威状态与版本，推送通道负责结果下发；长连接只用于推送，不承载动作校验与结算。
- 三种方案必须在三段上给出实质不同的形态：API 为单体承载与独立服务、状态存储为 Redis 与关系数据库（或两者分层）、推送为长连接网关与长轮询，不能只更换技术名称而边界相同。
- 每次动作写入状态存储后，先持久化成功再推送；推送失败不影响结算结果，由客户端重连后按版本补偿。
- 判定：若方案把结算逻辑放进长连接进程、对局状态只驻留进程内存而无持久化，或推送与结算必须同进程才能工作，则不满足异步对战要求，必须重画三段边界。

### 容量指标

- 对局并发：`对局并发 = 峰值在线玩家 ÷ 每局参与人数 × 同时在局比例`；异步对局未结束期间持续占用状态存储，按「进行中对局总数」单独统计，不能只按此刻在线玩家推算。
- 动作 QPS：`动作 QPS = 对局并发 × 每局每分钟动作数 ÷ 60 × 峰值集中系数`；动作频率按回合节奏与每回合动作数估算，不使用 tick 频率，日活不能直接当作 QPS。
- 状态读写：`状态读 QPS = 动作 QPS + 重连与刷新读取`，`状态写 QPS = 动作 QPS × 每次动作写入次数`；状态存储容量按 `进行中对局总数 × 单对局状态大小` 估算，含版本与日志开销。
- 推送连接数：`推送连接数 = 峰值在线玩家 × 每玩家连接数`，区分对局推送连接与大厅连接；异步对局在玩家离线时不保留长连接，按在线玩家而非对局参与者统计。
- 对局持久化量：`日均新增持久化量 = 日均新增对局数 × 单对局持久化字节`，`对局持久化总量 = 日均新增持久化量 × 保留天数`，单对局字节含状态快照与动作日志，并写明归档或清理策略。
- 判定：每个方案都能按上述公式复算出对局并发、动作 QPS、状态读写量、推送连接数与持久化量，并标注假设与峰值集中系数；缺少任一项即视为容量推算不完整。

### 平滑扩容

- API 无状态，直接水平扩展；会话与鉴权信息不写进程内存，新实例可立即接管请求。
- 对局按对局 ID 分片：同一对局的动作串行落在同一分片，分片内以对局为并发单元；新增分片只承接新对局，进行中对局不迁移。
- 推送通道独立扩展，按连接数扩容；推送节点故障时客户端重连并重订阅其所在对局，不重新结算。
- 判定：扩容期间进行中对局不中断，新对局落到新分片；扩容触发指标（API 的请求延迟与 QPS、分片的对局数、推送节点的连接数）与阈值写入方案，并能对应到具体监控量。

### 常见陷阱

- 重复提交与重放：客户端因超时或重试重复发送同一动作，导致重复结算。动作必须携带客户端生成的 `actionId` 与对局内递增序号，服务端按对局维度去重，重复 `actionId` 返回首次结果；仅依赖 HTTP 方法幂等或时间窗过滤会让合法重试被误判或漏判。
- 同一回合并发动作竞态：两个玩家在同一回合同时提交，后写覆盖先写。回合内动作按 `(对局 ID, 回合号, 顺序)` 串行处理，或写入时带乐观锁版本；无条件覆盖即视为缺陷。
- 超时自动动作：已到回合时限但玩家未提交，服务端以服务端时钟判定超时，并按可复现规则自动执行默认动作且只执行一次；依赖客户端上报超时或让对局无限挂起都不符合要求。
- 状态版本冲突：客户端基于旧版本提交动作，服务端按版本条件更新并在冲突时拒绝，返回当前状态与版本让客户端重放；无条件写入会让已结算的回合被回滚。
- 随机数可预测：客户端能预测下一回合抽牌或暴击结果并据此选择动作；随机数必须由服务端生成、记录并进入对局日志，客户端不得接触种子。

## 步骤

1. 按[服务架构方案通用要求](requirements.md)读取产品需求、产品描述、用户规模与现有实现，判定属于回合请求-响应、异步对战；不属于时按[服务架构方案生成](index.md)的场景路由改选分册。
2. 按通用要求的三种方案要求与输出位置生成方案，只展开回合制差异部分：同步链路、权威边界、无状态 API／对局状态存储／推送通道的三段拆分。
3. 按「容量指标」公式为每个方案计算对局并发、动作 QPS、状态读写、推送连接数与对局持久化量（日均新增量与总量），记录假设与峰值集中系数，写入该方案的平滑扩容部分。
4. 为每个方案写明动作幂等、回合串行或版本冲突处理、超时自动动作、断线恢复方式，以及「常见陷阱」的规避方式；给出 API、分片与推送通道各自的扩容触发指标与阈值。
5. 按通用要求给出对比表与推荐方案，取得用户选择后按[服务端方案实现](../implementation.md)细化选定方案。

## 验证

- 动作幂等：同一 `actionId` 重复提交多次，对局状态与首次提交一致，只结算一次，重复请求返回首次结果而非报错。
- 状态版本冲突被拒绝：以过期版本提交动作时，服务端返回冲突与当前状态版本，不覆盖已结算回合；客户端重放后状态收敛。
- 超时结算正确：服务端时钟越过回合时限后，自动动作执行且仅执行一次，结果符合规则并可复算；玩家在超时后提交的迟到动作被拒绝或按规则处理，不产生二次结算。
- 断线后可恢复对局：新连接携带对局 ID 与客户端已知版本，可重建至最新回合；恢复后不重复下发已确认的结算，跨天异步对局在服务端重启后仍可继续。
- 容量可复算：每个方案能按公式复算出对局并发、动作 QPS、状态读写、推送连接数与持久化量，并标注假设与峰值集中系数。
