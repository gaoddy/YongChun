# Runbook：休闲与小游戏架构

## 适用场景

- 设计休闲游戏、小游戏合集与单机弱联网的服务端架构。
- 适用于无实时对局或仅有异步对局、以客户端本地结算为主的产品；不适用于要求服务端权威实时推进的对局，需按[服务架构方案生成](index.md)的场景路由改选分册。

## 规则

### 同步模型

- 不设实时对局，或仅有异步对局；游戏过程在客户端本地推进，服务端只在关键节点介入：校验结果、写入云存档、处理支付回调、更新排行。
- 客户端本地结算，服务端校验关键结果与支付回调：客户端上报结算结果时附带可复算的输入摘要，服务端按同一规则复算并比对；偏差超出容差的结果拒绝入库。
- 判定：若服务端在每一局游戏过程中持续推送状态或要求固定 tick 同步，则不属于本场景；若服务端对客户端上报的分数、奖励、货币变化不做复算直接采信，则校验缺失，必须补上复算规则。

### 云存档

- 云存档至少记录存档内容、写入时间、版本号与设备标识；冲突解决策略必须在方案中写明为按时间取新、按版本号取大或由用户选择其一，不允许留空。
- 离线数据合并规则明确：客户端离线期间的进度、奖励与消耗，在联网同步时按同一存档字段口径逐项合并，而不是整份覆盖；合并方向与字段优先级写入方案。
- 判定：若两个设备先后写入同一存档且没有版本号或时间戳可比较，或方案只写「以最新为准」却不说明「最新」按服务端时间、客户端时间还是版本号判定，则冲突策略不成立；若离线数据同步时整份存档覆盖服务端，导致离线期间另一设备所得进度丢失，则合并规则不成立。

### 候选架构差异

- 四段拆分：无状态 API 负责登录、存档读写与结果校验入口；对象存储负责存档正文与资源文件；排行缓存负责榜单读写；支付回调独立入口负责支付平台通知。
- 弱在线方案必须说明离线可玩范围：哪些玩法与进度可在离线时产生、哪些必须联网、离线产物在恢复联网后如何校验与合并。
- 三种方案必须在四段上给出实质不同的形态：API 为单体承载与独立服务、存档为对象存储与关系数据库、排行为内存缓存与托管有序集合、支付回调为同进程入口与独立服务；不能只更换技术名称而边界相同。
- 判定：若方案把存档正文直接放在 API 进程内存、把排行与存档写在同一强一致事务而无法分开扩容，或支付回调与游戏 API 无独立限流边界，则不满足四段拆分；弱在线方案未写离线可玩范围即视为未覆盖场景。

### 容量指标

- `DAU 峰值 = 最终日活 × DAU 峰值集中系数`，单位为「人/日」，集中系数为无量纲比值，按上线活动与时段分布取值并写明依据。
- `存档读 QPS = DAU 峰值 × 人均每日存档读次数 ÷ 86 400 × 峰值集中系数`，`存档写 QPS = DAU 峰值 × 人均每日存档写次数 ÷ 86 400 × 峰值集中系数`，单位为「次/s」。
- `排行更新 QPS = DAU 峰值 × 人均每日排行更新次数 ÷ 86 400 × 峰值集中系数`，单位为「次/s」；榜单容量按 `榜单条目数 = 榜单数 × 每榜条目数` 估算，单位为「条」。
- `支付回调日总量 = DAU 峰值 × 付费率 × 人均每日付费笔数`，单位为「笔/日」；`支付回调峰值 QPS = 支付回调日总量 ÷ 回调峰值窗口秒数`，单位为「笔/s」，峰值窗口按支付平台通知的实际集中时段取值。
- `存档存储量 = 注册用户总数 × 单用户存档份数 × 单存档平均字节`，单位为「字节」；`日均存档增长量 = DAU 峰值 × 人均每日存档写次数 × 单存档平均字节`。
- 判定：每个方案都能按上述公式复算出 DAU 峰值、存档读写 QPS、排行更新 QPS、支付回调峰值 QPS 与存档存储量，并标注人均次数、付费率、峰值集中系数与峰值窗口的取值依据；日活直接当作 QPS，或公式中任一变量未定义，均视为容量推算不完整。

### 平滑扩容

- API 保持无状态，登录态与限流计数放在共享存储，实例可随时增删而不丢会话。
- 存档按用户 ID 哈希分片，同一用户的读写落在同一分片；新增分片只承接新用户，已有用户不迁移。
- 排行分榜：全局榜、分区榜与好友榜分开存储与更新，读写压力不集中到单一键；榜单按周期归档而不是原地无限增长。
- 静态资源与资源包走 CDN，服务端不回源承载大文件下载。
- 判定：扩容触发指标（API 的 QPS 与延迟、存档分片的单分片 QPS 与容量、排行缓存的单键写入 QPS、支付回调入口的队列积压）与阈值必须写入方案并对应到具体监控量；只写「支持水平扩展」而无阈值即不满足要求。

### 常见陷阱

- 本地存档篡改：客户端可直接改写本地文件后上报。服务端必须对进度关键字段做签名或复算校验，签名密钥不下发到客户端；仅校验字段范围而不校验来源即视为缺陷。
- 云存档冲突：多设备交替写入导致高进度被低进度覆盖。写入必须带版本号条件，条件不满足时返回当前版本与冲突，由客户端按已声明的策略合并或让用户选择。
- 排行刷分：客户端伪造分数或高频提交刷榜。排行入口必须校验分数来源（服务端复算或对局凭证）、按用户与设备限频，并保留异常分数回滚能力；只看提交值即视为可刷。
- 支付回调重复：支付平台重试通知导致重复发货。回调必须按平台订单号幂等处理，先落去重记录再发货，重复通知返回成功且不重复发放；仅用内存集合去重，重启后即失效。
- 离线数据合并出错：离线期间的奖励与消耗在联网后重复发放或丢失。合并必须按操作唯一 ID 去重，按字段优先级合并，并在合并前后保留可回退的存档版本；整份覆盖或不做去重即视为缺陷。

## 步骤

1. 按[服务架构方案生成](index.md)读取产品需求、产品描述、用户规模与现有实现，判定确属休闲、小游戏合集或单机弱联网；不属于时回到入口按场景路由选择分册。
2. 按入口的三种方案要求与输出位置生成方案，只展开本场景差异部分：无状态 API、对象存储、排行缓存、支付回调的四段拆分，以及弱在线方案的离线可玩范围。
3. 按「容量指标」公式为每个方案计算 DAU 峰值、存档读写 QPS、排行更新 QPS、支付回调峰值 QPS 与存档存储量，记录人均次数、付费率、峰值集中系数与峰值窗口的假设，写入该方案的平滑扩容部分。
4. 为每个方案写明云存档冲突策略与离线数据合并规则、结果校验方式、排行防刷与支付回调幂等方案，以及 API、存档分片、排行缓存与支付入口各自的扩容触发指标与阈值。
5. 按入口要求给出对比表与推荐方案，取得用户选择后按[服务端方案实现](../implementation.md)细化选定方案。

## 验证

- 存档冲突可解决且可回退：两设备写入同一存档时，按声明的策略产生确定结果，冲突时不静默覆盖；保留上一版本，可在合并结果错误时回退。
- 排行防刷：伪造来源或高频重复的分数被拒绝或标记，正常提交不受影响；异常分数可回滚且不影响其他玩家名次。
- 支付回调幂等：同一平台订单号重复通知多次，只发放一次；服务重启后重复通知仍不重复发放，重复请求返回成功。
- 离线恢复后数据一致：离线期间产生的进度、奖励与消耗在恢复联网后只合并一次，多次同步结果一致，与在线期间同口径操作的结果相等。
- 容量可复算：每个方案能按公式复算出 DAU 峰值、存档读写 QPS、排行更新 QPS、支付回调峰值 QPS 与存档存储量，并标注全部假设。
- 三种方案在 API、存档、排行与支付回调的边界形态上有实质差异，且均覆盖全部产品需求与最终用户规模。
