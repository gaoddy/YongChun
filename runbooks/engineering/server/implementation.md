# Runbook：服务端方案实现

## 适用场景

- 产品改动与架构方向已确认，编写 `update/<需求>/technical.md` 的服务端实现方案。
- 不影响产品的纯技术改动，直接编写 `technical.md` 的服务端实现方案。
- 架构方向未定、需要重新比较技术形态时，先按[服务架构方案生成](architecture-options.md)选择，不在本文比较架构。

## 前置读取

- [服务端分层](layering.md)

## 实现要点

| 维度 | 方案中必须写明 |
| --- | --- |
| 改动边界 | 受影响的服务端模块、接口、表与生成物，逐项对应 `product.md` 的规则 |
| 分层落点 | 逻辑放入 handler / domain / application / infrastructure 的哪一层；新增端口由谁定义、由谁实现、在何处装配 |
| 接口契约 | 路径、方法、请求与响应字段、错误码、分页与过滤；复用或新增 `/api/v1/...` 接口 |
| 数据 | schema 变更、约束与不变量、事务边界、幂等键；迁移形式按[项目阶段](../../../AGENTS.md#项目阶段) |
| 并发与一致性 | 锁、隔离级别、重试与去重、缓存一致性、跨服务写入顺序 |
| 可观测性 | 关键日志字段、指标、错误码与告警触发点 |
| 失败与降级 | 外部依赖的超时、重试、熔断、降级与补偿 |
| 测试设计 | 端到端测试覆盖的链路与真实依赖，`<e2e 入口>` 执行范围 |

## 实现约束

- 在已选定的架构与技术选型内细化，不重新比较架构方案，不引入未经确认的技术；确需变更架构或选型时，回到[服务架构方案生成](architecture-options.md)重新选择，选型变更按[技术选型变更](../tech-change.md)执行。
- 容量与扩展以选定架构方案为基线，见[服务架构方案生成](architecture-options.md)；本文只说明本改动对容量与扩展的影响及实现方式，不重写容量基线与扩容路径。
- 实现方式的选择只影响代码组织、执行顺序与落地步骤，不改变对外契约、数据模型与部署形态。

## 步骤

1. 读取已确认的 `product.md`、选定的架构方案与版本 `technical/` 基线，确认本次改动落在既定架构内。
2. 按实现要点逐项写出方案，标注涉及的模块、接口、表与文件位置。
3. 存在多种实现方式时写明选择与理由，只比较实现层面，不重新比较架构方案。
4. 未确认的事项写入版本 `open-questions.md`，不在方案中留待定分支。
5. 与用户确认方案后，把 `technical.md` 状态改为「方案未实施」，并把确认结论同步到版本 `technical/` 基线。
6. 方案变更时更新原文件，不新建目录或副本。

## 验证

- `product.md` 中每条产品规则都能在方案中找到对应实现位置。
- 接口、schema 与生成物的变更点均可定位到具体文件与命令。
- 依赖方向与装配符合[服务端分层](layering.md)的约束。
- 方案只使用选定架构与技术选型，未引入未经确认的架构变更或新技术。
- 容量与扩展影响符合选定架构方案的基线，未另写一套容量推算。
- 未确认事项已进入 `open-questions.md`，方案中无未决分支。
