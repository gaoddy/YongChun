# Runbook：数据模型变更

## 适用场景

- 新增或修改表、字段、索引、约束，或调整迁移。
- 建表前的表划分、字段与索引规划见[数据库表规划](table-design.md)。

## 数据库迁移

- 迁移形式取决于项目阶段：
  - **开发阶段**：schema 改动直接修改基线迁移文件 `<baseline 文件>`，不新增按序编号的迁移文件。
  - **已上线**：基线文件冻结不再修改；所有 schema 改动一律新增按序编号的 migration 文件。
- 迁移工具若按文件名记录已应用迁移且不校验 checksum，修改 baseline 只对新库和重建库生效；已应用过旧 baseline 的库不会自动获得变更，须重建或单独处理。
- 迁移文件只做 schema 变更与必要的数据回填，不写业务逻辑；每次迁移在本地与 e2e 环境各执行一次。
- 已上线环境的迁移必须兼容仍在运行的旧实例：先加列与索引、回填数据，再切换读写；删除与重命名放到后续版本。

## 数据库不变量

- 不变量优先用声明式约束（CHECK、UNIQUE、部分唯一索引、外键、NOT NULL）或应用层同一事务内的显式写入实现；不新增数据库 FUNCTION / 触发器 / 存储过程。例外仅限标准约束无法表达且必须防止旁路写入的场景，须在迁移文件中注释理由。
- 应用层校验只做友好提示，不作为唯一防线；绕过 API 的写入也必须被约束拦住。

## 数据层约束

- 真相源：数据库是唯一真相源，缓存只做加速，可随时清空并从库重建。
- 事务边界：一次请求一个事务，在 application 层显式开启；跨表写入在同一事务内完成，不在循环中提交。
- 查询：列表与过滤查询必须有可用索引；禁止 N+1；分页使用游标或稳定排序键；大字段不进列表查询。
- 锁与并发：写路径明确锁粒度与冲突处理；高冲突场景用幂等键或唯一约束兜底，不用重试掩盖竞态。
- 缓存键：`<业务>:<对象>:<id>` 结构，带版本前缀便于整体失效；写库后先更新库再删除缓存，不先写缓存。
- schema 文档：每张表在 `docs/technical/<模块>/models/` 下对应一个文件，同步建表或基线迁移中的定义，并列出 `keypath` 字段表与主键、索引、约束，形式见[文档结构](../../docs/structure/docs-structure.md#数据结构文档)；迁移与文档在同一任务内更新。

## 步骤

1. 判断项目阶段：开发阶段直接修改基线迁移；已上线新增按序 migration 文件。
2. 选择不变量的表达方式：优先声明式约束，其次同一事务内的应用层写入。
3. 修改 schema、查询与缓存代码，保持事务边界与不变量。
4. 在本地与 e2e 环境执行迁移，验证重建与升级两条路径。
5. 在 `docs/technical/<模块>/models/` 更新表文档：同步原始定义与字段表，补主键、索引与约束。
