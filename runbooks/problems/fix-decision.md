# Runbook：修复决策

## 适用场景

- 排查已确认根因，需要决定修在哪一层、改哪一端、修到什么程度。
- 不用于排查本身（见[问题排查](../problems/troubleshooting.md)）；改变产品规则或接口契约的缺陷走版本 `update/`。

## 前置读取

- [问题排查](troubleshooting.md)

## 决策点

- 多个修复方案比较时，只按架构合理性、可维护性、可扩展性与长期演进能力、部署上的平滑扩展能力，以及性能、资源占用、响应延迟和吞吐比较；不因工程难度、改造成本、历史包袱或兼容负担降低标准。

| 决策点 | 规则 |
| --- | --- |
| 修复层次 | 修在根因所在层，不在调用方或入口加兜底掩盖症状 |
| 修改端 | 优先修改 API；只有 API 修改成本较高时才修改客户端。API 可集中发布并立即覆盖全部客户端，客户端修改受版本分发与用户升级节奏限制 |
| 修复范围 | 最小改动，不扩展功能、不顺带重构；同一根因引起的多处症状一并修，不同根因分开处理 |
| 兼容 | 按[项目阶段](../../AGENTS.md#项目阶段)的兼容要求执行；当前阶段不保留旧版兼容逻辑 |
| 修复失效 | 连续 3 次修复无效时停止打补丁，回到架构层面质疑设计，与用户确认后再改 |
| 记录 | 根因、影响范围与修复方案写入 `bugfix/<日期>-<slug>/bugfix.md`；方案未确认时同步写入版本 `open-questions.md` |

## 步骤

1. 核对排查结论：根因、影响范围、复现条件齐备，缺失时回到[问题排查](../problems/troubleshooting.md)。
2. 按决策点确定修复层次、修改端与范围；涉及产品规则或接口契约变更时改走版本 `update/`。
3. 先写失败用例，确认能稳定复现根因。
4. 实施单一修复，只改决策范围内的文件。
5. 验证修复，回写测试与文档，按缺陷修复流程清理 `bugfix/` 目录。

## 验证

- 失败用例修复前失败、修复后通过。
- 端到端测试通过：`<e2e 入口>`
- 修复未引入新的失败项；跳过或放宽的用例已说明原因。
- `bugfix.md` 中的根因与修复方案和实际改动一致，文档与测试已同步。
