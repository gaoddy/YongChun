# Runbook：解释与讲解

## 适用场景

- 需要向特定受众解释代码、概念、报错或方案，如用户说「ELI5」「解释一下」「讲给老板听」「让我妈也能听懂」，或直接点名受众。
- 面向仓库文档的撰写与修改见[文档写作](docs-writing.md)，不按本文调整受众，按文档规则写。

## 前置读取

- [问题排查](../problems/troubleshooting.md)：解释报错或异常前先确认根因，不把表面症状当原因。

## 受众判定

- 从请求中提取受众：年龄、学历、岗位或关系，取最先出现且最具体的一类。
- 未给出受众时按 5 岁档处理，保持成人语气，不刻意幼儿化。
- 受众同时符合两档时取更严格的一档，例如「不懂技术的产品经理」按非技术受众表达、按产品经理组织重点。

### 年龄段

| 受众 | 表达方式 |
| --- | --- |
| 5 岁 | 玩具、动物、糖果、操场做类比；短句，一句一个概念 |
| 10 岁 | 小学水平；能理解简单因果；用学校、运动、游戏做类比 |
| 15 岁 | 青少年；能接受少量抽象；用社交媒体、手机、游戏做类比；语气略随意 |
| 20–30 岁 | 清晰直接；用日常生活、工作、金钱做类比 |
| 40 岁以上 | 尊重语气；用置业、职业、家庭管理做类比 |

### 学历

| 受众 | 表达方式 |
| --- | --- |
| 小学五年级 | 简单词汇与具体例子，不使用术语 |
| 初中 | 可引入基础术语并当场解释；按步骤推理 |
| 高中 | 中等复杂度；术语可以出现，但需要解释 |
| 大学 | 学术框架；术语加简短背景；理论结合应用 |
| 研究生 | 预设扎实基础；讲细节、取舍、边界情形与深层影响，保持精确 |

### 岗位

| 受众 | 关注点 | 组织方式 |
| --- | --- | --- |
| 管理者 | 影响、时间、风险、成本 | 业务结果、团队影响、需要拍板的选项 |
| 工程师 | 原理、架构、取舍 | 实现细节、性能、可维护性 |
| 设计师 | 用户体验、视觉与流程 | 对用户的影响、交互模式、可访问性 |
| 总监 | 战略、ROI、竞争优势 | 全局、市场位置、资源分配 |
| 同事 | 实际上下文与协作 | 对他的工作有什么影响、需要知道什么 |
| 产品经理 | 用户价值、优先级、范围 | 功能影响、该做什么与不做什么 |

### 关系

| 受众 | 语气 | 类比来源 |
| --- | --- | --- |
| 伴侣 | 温和、口语、耐心 | 家务、共同经历、日常作息 |
| 父母 | 尊重、清楚、不说教 | 他们熟悉的设备、家庭事务 |
| 孩子 | 活泼、鼓励、短句 | 游戏、动画、学校、动物 |
| 朋友 | 随意、可幽默 | 流行文化、共同兴趣 |

## 解释结构

1. 第一句说清本质（what），结论先行。
2. 用受众已经知道的事物做类比。
3. 按受众档位分层补细节，只加该档能接住的部分。
4. 收尾说明「这对你意味着什么」：影响、决策或下一步。

## 语言校准

### 非技术受众

- 不使用术语；必须使用时就地定义。
- 一句一个概念。
- 具体优于抽象，例如「服务器像餐厅服务员」优于「服务器处理客户端通信」。
- 用「你」「你的」把内容落到对方身上。

### 技术受众

- 使用准确术语，省略术语会被视为轻视对方。
- 讲取舍、边界情形与设计决策，不复述基础。
- 用对方已知的结构对照，例如「像哈希表，但……」。

### 业务受众

- 先讲影响与结果，能量化就量化。
- 不展开实现细节，除非对方追问。
- 落到决策：「这意味着我们应该……」。

## 语气

- 5–10 岁：热情，像喜欢的老师讲一件有意思的事。
- 青少年：略随意，但不刻意讨好。
- 专业人士：自信、清楚，尊重对方的判断力，只在知识缺口处搭桥。
- 家人：耐心、温和，像饭桌上聊天。

## 边界

- 不居高临下：面向孩子的解释要有趣，面向管理者的解释要让人能做决定，不暗示对方笨。
- 解释代码先讲目的再讲机制：先说明它为什么存在，再讲语法与实现。
- 允许为讲清核心概念简化，但简化不等于编造：可以省略细节、使用不精确的类比，不得给出与事实相反的结论；未核实的机制标注「未核实」。
- 解释报错先确认根因，根因未确认时按[问题排查](../problems/troubleshooting.md)定位后再讲。
- 篇幅随受众：孩子短，技术受众可长；同一问题对不同受众给不同长度。
- 代码、命令、路径与标识符保留原文，不翻译；正文用中文。

## 步骤

1. 判定受众：按请求中的年龄、学历、岗位或关系选档；未给出时按 5 岁档，跨两档时取更严格的一档。
2. 读懂素材：读相关代码或文档；解释报错时先按[问题排查](../problems/troubleshooting.md)确认根因。
3. 按结构组织：一句话本质 → 类比 → 分层细节 → 对受众意味着什么。
4. 按语言校准与语气改写，核对术语使用与篇幅。
5. 自检：受众能否用自己的话复述核心结论；不能则重写类比或删减细节。

## 验证

- 受众档位有明确依据：请求点名，或按默认 5 岁档；跨类已取更严格的一档。
- 第一句给出本质，结尾说明对受众的影响或下一步。
- 非技术受众没有未解释的术语；技术受众保留了准确术语与取舍。
- 内容基于已读懂的素材；报错解释已确认根因；未核实部分已标注。
- 篇幅与受众匹配，代码、命令、路径与标识符保留原文。
