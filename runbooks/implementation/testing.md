# Runbook：补充测试与验证

## 适用场景

- 新增功能、修复缺陷或调整接口后补充测试与执行验证。

## 前置读取

- [Make 构建入口](make.md)

## 测试范围

- 只测试本次改动涉及的功能：改动直接对应的入口、分支与依赖链，以及受其直接影响的调用方。
- 不执行全量测试，不回归与本次改动无关的功能；仓库既有测试全量通过不构成本任务的验收条件。
- 改动跨模块时按实际调用链扩大范围，不按目录、文件数量或「顺手一并测」扩大。
- 影响面不明确时，先检索该功能的调用方与引用确定范围；仍无法确定时只跑该功能的端到端路径，并在交付说明中写明未覆盖的部分。
- 例外：合并队列交付按[Worktree 合并队列交付](../delivery/worktree-delivery.md)执行定向与全量验证。

## 测试同步

- 功能改动时同步更新对应测试：行为改了，覆盖该行为的测试在同一交付内一起改，不留仍按旧行为断言的用例。
- 新增入口、分支、参数或错误码时补上对应测试；删除、合并或重命名功能时同步删除、合并或改名其测试。
- 测试未随功能更新时任务不算完成；不得用注释、跳过或放宽断言让旧测试通过。
- 只同步本次改动涉及的测试，不连带改写在范围内无关的测试。

## 服务端测试策略

- 不维护单元测试文件，只保留端到端测试及其 `<e2e 入口>`；临时验证产生的其他测试文件、fixture、testdata 及测试专用支持文件不得随交付提交。
- 例外：并发、分片与关键状态机的长期回归测试保留，随交付提交；不新增其他单元测试。
- e2e 使用真实依赖（`<数据库>`、连接池、`<缓存>`）；核心链路的 SKIP 不算通过。
- e2e 缺少依赖时先启动环境，不允许改为 mock。

## 客户端测试策略

- 测试仅在开发任务分支内临时保留：按改动范围编写并执行，验证完成后删除全部测试及其专用支持文件（含 fixture、golden、integration / driver），不得合入长期分支。
- 删除后执行 `<静态检查命令>`，并至少回查一次真实接口或关键页面数据。
- 实机验证优先使用稳定设备与非 debug 构建。

## 步骤

1. 按本次改动涉及的功能选择测试层级，优先真实依赖的端到端测试；范围外的用例不执行。
2. 明确成功、失败与边界用例，覆盖权限与异常路径。
3. 同步更新本次改动涉及的现有测试，使其与新行为一致。
4. 执行验证矩阵，记录命令输出与退出状态。
5. 修复失败项，不通过跳过、注释或放宽断言处理。
6. 交付前清理临时测试与 fixture，保留需要长期回归的测试。

## 验证

- 验证矩阵全部通过，核心链路的 SKIP 不算通过。
- 执行的测试只覆盖本次改动涉及的功能，没有执行全量测试或无关功能的回归。
- 本次改动涉及的测试已随功能更新，不存在仍按旧行为断言的用例。
- 关键链路有对应测试，失败信息足以定位问题。
- 文档中的测试命令与仓库一致。
