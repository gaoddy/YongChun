# Runbook：任务执行与交付

## 适用场景

- 需要修改代码、文档或配置的任务。

## 前置读取

- [Worktree 与分支](worktree.md)

## 场景判定

修改类请求按用户表达自动判定场景，读取对应 runbook 执行，不需要用户说出命令：

| 用户表达 | 判定 | 进入 |
| --- | --- | --- |
| 报错、异常、不对、坏了、修一下 | 缺陷 | [缺陷修复](../version/bugfix.md)、[问题定位](../problems/troubleshooting.md) |
| 改成、新增、去掉、调整规则或行为 | 需求变动 | [需求变动](../version/requirement-change.md) |
| 想加功能、需求还不清楚 | 功能需求澄清 | [产品功能需求澄清](../product/feature-requirements.md) |
| 需求已确认、能不能做、技术可行性、与现有功能冲突 | 可行性调研 | [产品功能可行性调研](../product/feature-feasibility.md) |
| 样式、布局、颜色、间距、交互、体验 | UI | [UI 设计](../product/ui/ui-design.md) |
| 新接口、参数、字段、错误码 | 接口 | [新增接口](../engineering/server/new-api.md) |
| 建表、表结构、字段与索引规划 | 表规划 | [数据库表规划](../engineering/database/table-design.md) |
| 表、索引、迁移、列类型 | 数据模型 | [数据模型变更](../engineering/database/schema-change.md) |
| 领域模型、DTO、枚举、结构字段 | 数据结构 | [数据结构设计](../engineering/data-structure-design.md) |
| 复杂问题、抽象建模、算法、复杂度 | 算法设计 | [算法设计](../engineering/algorithm-design.md) |
| 同步文档、补说明 | 文档 | [文档回写](../docs/docs-sync.md) |
| 升依赖、换库、升级版本 | 技术变更 | [技术变更](../engineering/tech-change.md) |
| 目录、模块位置、命名 | 结构 | [目录结构](../engineering/directory-structure.md) |

- 命中即执行，不反问是否走流程，也不需要用户指定命令。
- 多场景同时命中时读全部相关 runbook，按依赖顺序执行。
- 仅在产品规则、验收标准不明确，或改动会改变对外行为时提问确认。
- 判定为缺陷时先定位根因再改代码；改变产品规则或对外行为的走需求变动，不按缺陷处理。

## 工程流程约束

### 构建入口

- 构建、测试、静态检查、生成、迁移与本地启动统一通过 `make` 目标执行，见 [Make 构建入口](make.md)；不手写等效命令，CI 与本地使用同一套目标。

### 任务流程

- 只读任务不建 worktree；修改仓库文件 → 从 `develop` 建 worktree 与分支 → 大改动在 `docs/plan/<分支名>/` 写实施计划 → 实施 → 验证 → 回写文档 → 提交 → 删除计划目录 → 合并 → 清理 worktree。
- 属于[小改动](worktree-timing.md)的任务直接在当前分支修改，不建 worktree，也不进入 plan 模式；只有大改动才启用 plan 模式与计划目录。
- 实施前确认任务范围与可验证的成功标准；实施中只改任务范围内的文件，不扩展功能、不顺带重构。

### 验证矩阵

| 改动类型 | 必须执行 |
| --- | --- |
| 代码 | 构建、静态检查、相关端到端测试 |
| 接口与契约 | 生成命令无差异，端到端测试覆盖新路径 |
| 数据模型 | 重建库迁移、端到端测试；已上线另加升级迁移 |
| 依赖 | 构建、静态检查、端到端测试、版本锁定检查 |
| UI | 静态检查、目标设备验证、浅色深色与多尺寸检查 |
| 文档与规则 | 相对链接校验、命令与路径核对 |

### 交付

- 交付链路：验证通过 → 同一任务回写文档 → `git diff` 自检 → 提交 → 合并 `develop` → 清理。
- 提交按主题拆分，一个提交一件事；消息写明范围与目的，不写「修改」「更新」这类无信息内容。
- 生成物按仓库约定随源契约提交；临时脚本、日志与测试专用文件不提交。
- 验证失败不得跳过、注释或放宽断言；修复后重跑完整矩阵。

### 计划

- 计划结构见[任务计划](../version/plan.md)：`index.md`、`task-plan.md`、`tasks/`；产品与技术结论链接 `update/`，不复制。
- 计划写在 `docs/plan/<分支名>/`，一个计划一个目录，只在实施计划时创建；`docs/plan/` 已忽略、不提交，任务完成后、合并前删除。

### 本地数据

- 临时种子数据与 mock 快照放在仓库忽略目录，不提交；mock 快照只用于本地调试，不作为验证通过的依据。
- 验证优先使用真实依赖与真实数据，见[补充测试与验证](testing.md)。

## 步骤

1. 明确目标、范围与可验证的成功标准，确认任务所属版本。
2. 创建 task worktree 与分支；分支基线为 `develop`，用户另有指定时除外。
3. 大改动进入实施计划时，在 `docs/plan/<分支名>/` 写计划；项目事实另有规定的从其规定。
4. 按任务边界实施，只改任务范围内的文件。
5. 按验证矩阵执行命令，记录输出与退出状态。
6. 同一任务内回写受影响文档，清理临时文件与测试专用文件。
7. 提交前检查 `git diff`，按主题提交。
8. 合并前删除计划目录，合并后清理 worktree。

## 验证

- 验证矩阵全部通过，失败项已修复而非跳过。
- `git diff` 只包含任务范围内的改动。
- 文档已回写，计划目录与临时文件已清理。
- 提交可追溯到任务与版本。
